## 1. 조사 결과 — 엔진은 이미 있고, 검증도 끝나 있습니다

새로 만들 것이 아닙니다.

| 있는 것 | 내용 |
|---|---|
| `saju.js` (303행) | 사주 4주. 국립천문대 기준으로 검증(20항목) |
| `fortune.js` (327행) | 일일 운세. **366명 × 120일** 표본으로 검증(20항목) |
| `solar-terms.json` | 24절기 2,424행 |
| `verify-saju.mjs` / `verify-fortune.mjs` | 배포 관문에서 매번 실행 중 |

`Fortune.of(내사주, 오늘사주)` 가 돌려주는 것:

```json
{ "scores": { "total":37, "money":48, "love":44, "work":46, "health":55, "study":56 },
  "grades": { "total": { "ko":"소길", "ja":"小吉" }, … },
  "god":    { "stem":"정인", "branch":"정관" },
  "el":     { "money":"금", "love":"수", … },
  "fit":    -6.6 }
```

**`god`(십신)이 핵심입니다.** 비견·겁재·식신·상관·편재·정재·편관·정관·편인·정인 —
사주에서 「오늘의 기운이 나에게 무엇인가」를 말하는 전통적 판단 축입니다.
점수는 여기서 나옵니다. 즉 **근거가 이미 실제 사주**입니다.

### 서버에서 도는 것을 확인했습니다

DOM 참조 **0건**. `globalThis` 에 붙는 방식이라 Node 의 `vm` 으로 그대로 읽힙니다.
`solar-terms.json` 은 `fetch` 대신 파일로 읽으면 됩니다.

## 2. 왜 「엔진 재사용」이지 「새 DB」가 아닌가

이용자는 사이트에서도 같은 운세를 봅니다. **두 곳의 값이 다르면 그 순간 신뢰가 끝납니다** —
「어제 사이트에서는 대길이었는데 LINE 은 소길」은 변명이 안 됩니다.

미리 계산해서 넣어두는 방식도 안 됩니다. 운세는 **(내 사주 × 그 날)** 이라
사람 수 × 101일만큼의 행이 생기고, 사람이 늘 때마다 다시 채워야 합니다.
엔진은 그 자리에서 계산하면 되고, 이미 그렇게 되어 있습니다.

**미리 만들어 둘 것은 「문안」입니다.** 엔진은 숫자와 십신을 주지만,
「오늘은 정인의 날이라 배움에 좋습니다」 같은 **말**은 사람이 써야 합니다.
그게 §4 의 DB 입니다.

## 3. 엔진 이식 — 사본을 만들지 않습니다

```
저장소       saju.js  fortune.js  solar-terms.json   ← 1부만 존재
  ↓ 사이트    Xserver 로 그대로 배포 (build-site.sh)
  ↓ 서버      .cpanel.yml 이 $APP/engine/ 로 복사
```

**server/ 안에 사본을 두지 않습니다.** 두면 웹과 LINE 의 운세가 갈라지는데,
갈라진 것을 알아채는 방법이 없습니다 — 양쪽 다 「정상으로 보이는 숫자」를 내므로.
배포할 때 저장소의 1부에서 가져옵니다.

`server/lib/fortune.mjs` 가 그 파일들을 `vm` 으로 읽어 감쌉니다.

## 4. 문안 DB — **결정 필요**

엔진이 주는 것으로 문안을 고릅니다. 키를 무엇으로 할지가 분량을 정합니다.

| 안 | 키 | 문안 수 | 평가 |
|---|---|---|---|
| (가) | 항목 × 등급 | 6 × 5 = **30** | 적지만 「왜」가 없음 |
| (나) | (가) + 십신 해설 | 30 + 10 = **40** | 근거가 보임. **권장** |
| (다) | 십신 × 항목 × 등급 | 10 × 6 × 5 = **300** | 다 쓰기 어렵고 품질이 떨어짐 |

**(나) 를 권합니다.** 항목별 한 줄 + 「오늘이 왜 그런가」를 십신으로 한 줄.
십신 10종은 뜻이 뚜렷해서 짧게 써도 근거로 읽힙니다.

문안은 **한국어 + 일본어 병기**로 씁니다 — 운세 자체가 한국어 교재가 됩니다.
「재물운」「대길」 같은 말이 매일 나오면 그것만으로 어휘가 붙습니다.

### 두는 곳

원고와 같은 이유로 **공개 저장소에 두지 않습니다**(`server/content/`).
표는 `fortune_lines` 를 새로 만들지, JSON 그대로 읽을지 — **결정 필요**.
지금 원고는 JSON → `content_templates` 로 넣고 있으므로 맞추는 편이 자연스럽습니다.

## 5. 어떻게 보낼지 — **결정 필요**

지금 하루치는 2통(문법+회화 / 단어)입니다. 운세를 어디에 넣을지.

- **(가) 3통째로 추가** — 운세가 독립적으로 읽힘. 알림이 늘지 않음(1회 push 에 묶임)
- **(나) 1통째 앞에 붙임** — 통수는 그대로. 대신 1통이 길어짐
- **(다) 운세만 별도 시각** — `lucky_hour_display`(그 사람의 길한 시각)에 보냄

**(가) 를 권합니다.** `pushMessage` 는 배열을 받으므로 3통이어도 API 호출은 1회,
알림도 1회입니다. (다)는 매력적이지만 배치가 사람마다 다른 시각에 돌아야 해서
cron 이 매시가 아니라 매분이 되고, 실패 시 되짚기가 어려워집니다.
