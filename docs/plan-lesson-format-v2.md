## 3. ★ 지시서 전제와 실제 코드가 어긋나는 곳

### 3-1 「fortune-server 17항목이 흔들린다」 — 흔들리지 않습니다

- 실물은 **19항목**입니다(`check(` 19회).
- 그중 `fortuneMessage` 를 부르는 것은 3곳(L168, L261, L274-275)이고,
  **세 곳 모두 `{bridge}` 를 넘기지 않습니다.**
- 따라서 L220-223 을 삭제해도 이 관문의 기대값은 **1건도 바뀌지 않습니다.**
  「바뀌는 것이 bridge 절 하나뿐임을 diff 로 증명」은, 이 관문에 관한 한
  **「diff 가 0줄임을 보이는 것」**이 됩니다.

실제로 깨지는 관문은 **`verify-push` 1항목**입니다.

```832:844:tools/verify-push.mjs
await check("その日の一言（fortune_bridge）は、原稿があるときだけ出る", async () => {
  const on = fortuneSection(WITH_SAJU, parsed, { load: () => FAKE_LINES });
  assert(/오늘은 재물운이 좋아요/.test(on.text), on.text);   // ← bridge 제거로 반드시 실패
```

그리고 같은 파일 L817-830 「운세는 3통째」가 **통수 기대값 4통**을 못 박고 있으므로,
🍀 를 레슨에 넣는 것 자체는 통수를 안 바꾸지만 **§3-3 의 퀴즈 결정에 따라 여기도 흔들립니다.**

> **보고 문안 정정 제안.** §7-3 「bridge 이중 출력 없음(운세 메시지 diff)」은

### 3-2 ★ 진짜 위험은 이중 출력이 아니라 **수신자 확대**입니다

지금 bridge 는 `fortuneSection()` 안쪽에 있습니다. 그래서 **아래 4관문을 전부 통과한 사람에게만** 갑니다.

```195:236:server/db/push-daily.mjs
export function fortuneSection(u, template, …) {
  if (!u.birth_date) return null;          // ① 생년월일 없음
  if (!u.birth_confirmed) … return null;   // ② 생년월일 미확인
  … if (!lines) … return null;             // ③ fortune-lines.json 미입고
  … if (!f) return null;                   // ④ 운세 엔진 실패
  return fortuneMessage(f, lines, { bridge: … });
}
```

bridge 를 `renderDay()` 로 옮기면 **이 4개 관문이 전부 사라집니다.** 사이트 진단을 안 거치고
LINE 만 친구추가한 사람(= `content-check` PROBES 3번째 「유이」와 같은 사람)에게도 🍀 가 갑니다.

**이행기에 이것이 어떻게 보이는가:**

```
🍀 今日のひとこと
今日の学習運がよいです。「고자」を一度声に出してみてください。
```

운세를 한 줄도 못 받는 사람에게 「学習運がよいです」가 갑니다. 렌더러만 먼저 배포하는
**바로 그 기간에**, 구양식 bridge 303개가 전부 이 모양입니다.

**대응안 3가지 (대표 확정 필요 — §6 A):**

| 안 | 내용 | 대가 |
|---|---|---|
| (가) | 🍀 는 **신양식(`pos` 있음)일 때만** 출력. 구양식은 통째로 생략 | 이행기에 🍀 가 아예 안 보임. 가장 안전 |
| (나) | 구양식 bridge 는 **종전대로 운세 말미**에 두고, 신양식만 레슨 하단으로 | 코드에 분기 2개. 「bridge 가 운세에 더 이상 없음」 관문이 성립 안 됨 |
| (다) | 지시서 문면 그대로(전원 출력) | 이행기 며칠 동안 위 문장이 전원에게 나감 |

**(가)를 권합니다.** §1-2 의 표에 「bridge 없음 → 🍀 생략」이 이미 있으니, 판정 기준을
「bridge 필드 유무」가 아니라 「`pos` 유무」로 읽으면 문면 수정 없이 (가)가 됩니다.

### 3-3 ★ 「퀴즈 매일 필수」가 만드는 충돌 3건 — 지시서에 없습니다

**(1) 절목 퀴즈와 같은 문제가 두 번 나갑니다.**
30/50/75일 절목 퀴즈의 출처는 **그날 원고의 `tpl.quiz` 바로 그것**입니다.

```603:609:server/db/push-daily.mjs
  if (atCheckpoint) {
    const q = learning.usableQuiz(tpl.quiz);      // ← 오늘 원고의 quiz
    if (q) { messages = [...messages, renderCheckpointQuiz(next, q)]; … }
  }
```

레슨 본문 ❓ 섹션도 `tpl.quiz` 를 쓰면, 30일차 아침에 **똑같은 문제가 본문과 절목 퀴즈로 2번** 갑니다.
bridge 이중 출력과 완전히 같은 종류의 사고이고, 지시서는 이쪽을 보지 않았습니다.

**(2) 3의 배수 복습 퀴즈와도 겹칩니다.**
`pickReviewQuiz` 는 `day_number <= next AND quiz IS NOT NULL` 에서 `ORDER BY RAND() LIMIT 1` 입니다.
지금은 51~101일에 quiz 가 없어 오늘이 뽑힐 일이 드물지만, **매일 필수가 되면 오늘도 후보**가 됩니다.
`WHERE day_number < next` 로 바꾸는 1줄 수정이 필요합니다.

**(3) LINE 5통 상한을 넘습니다.**
`quickReply` 는 **배열의 마지막 1통에서만 열립니다**(코드 주석 L600-601). 그래서 퀴즈를
「기존 quizMessage 방식 그대로」(§1-1) 내려면 **반드시 별도의 마지막 1통**이어야 합니다.

| 상황 | 지금 | 매일 퀴즈 도입 후 |
|---|---|---|
| 평시 | 본문2 + 운세 + 부적 = **4** | + 퀴즈 = **5** (상한 정확히) |
| 기한 예고일 | 본문2 + 운세 + 예고 + (부적 생략) = **5** | + 퀴즈 = **6 → LINE 400, 그 사람 아침 전체가 낙하** |
| 절목일(30/50/75) | 본문2 + 운세 + 부적 + 절목 = **5** | + 퀴즈 = **6 → 동일** |

`push-daily.mjs` 는 이미 `if (fortune && messages.length < 5)` 로 부적을 양보시키고 있지만,
퀴즈는 그런 장치가 없습니다.

**대응안 (대표 확정 필요 — §6 B·C):**

| 안 | 내용 |
|---|---|
| (가) | **3의 배수 복습 퀴즈를 폐지.** 매일 퀴즈가 있으면 복습 퀴즈는 존재 이유가 겹칩니다. 통수 1개 절약 |
| (나) | **절목 퀴즈를 폐지**하고 30/50/75 는 본문 ❓ 를 「🎯 절목」 라벨로 승격. 채점(`setQuizResult`)은 그대로 |
| (다) | ❓ 를 **Flex 버튼**으로 (저녁 복습 `renderReviewQuestion` 과 같은 방식) → 마지막 통이 아니어도 버튼이 남으므로 통수·순서 제약에서 해방. **단 §1-1 「quickReply 방식 그대로」와 충돌** |
| (라) | 부적과 같은 「5통이면 오늘은 쉰다」 규칙을 퀴즈에도 부여 → 「매일 필수」가 아니게 됨 |

**(가)+(나) 조합을 권합니다.** 매일 퀴즈가 들어오면 「3일 주기 복습」과 「절목」은 둘 다
같은 `tpl.quiz` 를 다른 이름으로 다시 꺼내는 것이 되어, 세 갈래가 한 우물을 파게 됩니다.

## 9. 트레이드오프

| 판단 | 택한 것 | 버린 것 |
|---|---|---|
| 구양식 처리 | **기존 조립 코드를 그대로 둔 채 신양식 갈래를 옆에 추가** | 하나의 코드로 통합. 통합하면 짧아지지만, 이행기 며칠 동안 「어제까지 잘 나가던 것」이 새 코드 경로를 타게 됨 |
| 신·구 판정 | `pos` 유무 1개 (지시서 확정) | tip 접두어·vocab 개수 등 복합 판정. 판정 기준이 여러 개면 「반쯤 신양식」인 원고에서 갈래가 갈림 |
| `isNewFormat` 위치 | `render.mjs` 에 두고 `content-check` 가 import | 각자 구현. 두 곳에 두면 렌더러는 신양식으로 보고 검사는 구양식으로 보는 날이 옴 |
| 品詞 표기 | 코드(`POS_LABEL`) 소유, `pos` 는 분류 키 | 원고의 `pos` 문자열을 그대로 헤더로 출력. 그러면 헤더가 303곳에 복제됨 |
| 🍀 수신자 | (권고) 신양식 한정 | 전원. 전원으로 하면 이행기에 운세 없는 사람에게 운세 문장이 감 |
| 퀴즈 통수 | (권고) 복습·절목 폐지로 통수 확보 | 셋 다 존치. 존치하면 LINE 5통을 넘는 날이 실재함 |
