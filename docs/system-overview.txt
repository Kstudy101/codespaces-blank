라우팅은 .htaccess 가 담당하고, 순서에 의미가 있습니다.

  1) HTTPS 로 몰기
     X-Forwarded-Proto 도 같이 봄. Xserver 는 SSL 종단이 앞단에 있어
     HTTPS 변수가 안 서는 구성이 있을 수 있음.

  2) www 로 몰기
     이 서버는 서버패널 설정으로 apex → www 301 을 이미 반환하고 있음.
     .htaccess 에 반대 방향(www 제거)을 쓰면
       apex →(서버)→ www →(.htaccess)→ apex → …
     로 무한 루프가 되어 사이트가 죽음. 서버 쪽 방향에 맞춰 둠.

  3) 중복 URL 정리
     /privacy.html → 301 → /privacy   (THE_REQUEST 를 보므로 4)와 충돌 안 함)

  4) 확장자 없는 URL 내부 재작성
       RewriteCond %{REQUEST_FILENAME} !-f
       RewriteCond %{REQUEST_FILENAME} !-d
       RewriteCond %{REQUEST_FILENAME}.html -f
       RewriteRule ^(.+?)/?$ $1.html [L]
     실파일·실디렉터리가 우선이므로 /kanji.json, /ogp.png 는 그대로 서빙.

  ※ SPA 폴백은 의도적으로 없습니다. 넣으면 없는 URL 도 200 이 되어 404 가 죽습니다.

캐시:
  .html / .js / .css  →  no-cache, must-revalidate
  공용 JS 에 파일명 버전이 없어서, HTML 만 갱신되고 JS 가 최대 1주일 낡게 남는
  조합을 막기 위함. no-cache 는 "저장하지 마라"가 아니라 "쓰기 전에 확인해라"
  이므로, 안 바뀌었으면 304 만 돌아옴.

보안 헤더:
  X-Content-Type-Options: nosniff / X-Frame-Options: SAMEORIGIN /
  Referrer-Policy: strict-origin-when-cross-origin /
  Permissions-Policy: geolocation=(), microphone=(), camera=()

비공개 보험:
  <FilesMatch "\.(db|sqlite3?|py|sh|md|yml|yaml)$"> Require all denied
  RewriteRule ^(data|tools|\.github)/ - [F,L]

■ saju.js — 사주 4주 (303행)

  기둥    결정 방식
  ------  ------------------------------------------------------------------
  년주    입춘(황경 315°)으로 전환. 설날도 원단도 아님
  월주    12개의 "절"로 전환. 중기(우수·춘분…)는 안 씀
  일주    60일 주기 산술. 진태양시 23시에 다음날로 넘김 (조자시. 야자시 불채용)

  · 표준시 이력을 값으로 박아둠
    서울은 1954-03-21 〜 1961-08-09 이 UTC+8:30, 양국 전후 서머타임까지 수록.
    IANA tz 데이터에서 일으킨 표. Intl 을 런타임에 안 부르는 이유는
    단말의 tz 데이터가 깎여 있어도 결과가 안 변하게 하기 위해서.

    도시 17개(한국 7 + 일본 10)를 목록에서 선택. 경도 직접 입력은 안 받음.
    도쿄 +19분, 서울 −32분으로 부호가 반대.

  · 균시차 (Meeus 28장)
    ±16분. 2시간 단위 시지가 경계에서 이것에 밀림.
    한때 부호가 반대로 들어가 있었고, 크기는 맞아서 화면으로는 못 잡았음.

  출력: year/month/day/hour, sajuYear, zodiac, elements(오행 개수),
        solar(진태양시 내역), city, notes(시각 불명·조자시 안내)


■ fortune.js — 오늘의 운세 6항목 (327행)

  난수를 안 씁니다. 같은 생년월일 + 같은 날짜면 반드시 같은 점수.
  갱신할 때마다 숫자가 바뀌면 "전회와 비교"가 의미를 잃음.

  세 항의 덧셈:

    항목       무엇                                    사람별  날짜별
    ---------  --------------------------------------  ------  ------
    ① 십신    내 일간 ↔ 오늘 간지 (음양까지 10종)     ○      ○
    ② 일진    오늘 오행 ↔ 항목 오행 (상생·상극)       ×      ○
    ③ 과부족  내 사주의 오행 편중                      ○      ×

  ①만 있으면 같은 날 전원이 같은 형태가 되고,
  ③만 있으면 매일 같은 숫자가 됨. 둘 다 있어야 "나의" "오늘" 운세가 됨.

  십신을 음양까지 봐서 10종으로 나눈 이유:
    오행만 5종으로 보면 갑과 을이 같은 취급이 되어 60일 일진이 25가지로 뭉개짐.
    연속한 2일이 동점이 되면 "전회와 비교"가 0 만 나옴.

  역법의 편향을 뺌:
    일진을 60일 일순시킨 평균(expected())을 항목마다 계산해 차감.
    안 하면 항목별 평균이 어긋나 "건강운만 매일 낮음"이 나옴.
    (지지 12개 중 토가 4개라 사주에 토가 많은 게 정상)
    기준 비율도 5등분이 아니라 천간(각 2/10)·지지(토만 4/12)에서 나온
    자연 비율 SHARE 를 씀.

  총운은 5항목 평균이 아님:
    평균을 내면 항목끼리 상쇄돼 누구의 어느 날을 봐도 중길만 나옴.
    대신 "오늘 온 오행이 내게 부족한 것을 메우는가"(fit)를 직접 봄.
    용신을 취하는 사고방식 그대로.

  등급 5단계: 대길 80 / 길 65 / 중길 50 / 소길 35 / 말길 0

  저장: localStorage["k101.fortune"] 에 날짜 + 정수 6개만.
        생년월일은 안 넣음 — 5,200만 통밖에 없어 해시로도 복원 가능하므로.
        동일인 확인을 안 하므로 표시는 "당신의 어제"가 아니라
        "전회 결과와 비교"이고 실제 날짜를 반드시 냄.

────────────────────────────────────────────────────────────────────────────────
  B-1.  HTTP 수신부 (app.mjs, 321행)
────────────────────────────────────────────────────────────────────────────────

프레임워크 없음(node:http). Express 를 넣으면 의존이 60개쯤 늘고
"검증은 설치 없이 돈다"는 성질이 무너짐.

  경로                      하는 일
  ------------------------  ------------------------------------------------
  POST /line/webhook        LINE 이벤트 4종
  POST /line/link/start     웹 사주를 맡아 state + 인증 URL 반환
  GET  /line/callback       LINE Login 착지점. JSON 이 아니라 HTML 화면 반환
  GET  /health              프로세스 + DB 까지 확인 (DB 가 죽으면 배송이 멈춤)

경로는 환경변수로 바꿀 수 있게 되어 있음
(LINE_WEBHOOK_PATH / LINE_CALLBACK_PATH / LINE_LINK_START_PATH).

기동 시 두 가지를 먼저 검사하고 안 되면 exit(1):

  1) LINE_CHANNEL_SECRET, DB_HOST, DB_USER, DB_PASSWORD, DB_NAME
     빠진 것을 이름으로 전부 나열하고 멈춤.
     1개씩 예외를 내면 "고치고 돌리고 다음에서 멈추고"를 반복하게 됨.

  2) LINE_API_BASE / LINE_AUTH_BASE 가 설정돼 있으면 정지
     시험용 주소를 남긴 채 뜨면 액세스 토큰과 채널 시크릿을 엉뚱한 호스트로
     계속 보내게 됨. 상대가 200 만 주면 화면상으로는 정상.
     ALLOW_FAKE_LINE=1 을 같이 둘 때만 허용.

CORS 는 * 가 아님:
  ALLOWED_ORIGINS 화이트리스트 + Vary: Origin.
  생년월일을 받는 입구이므로 어디서든 던져 넣을 수 있게 둘 이유가 없음.
  쿠키를 안 쓰므로 credentials 도 불허.
  Origin 이 없는 요청(브라우저 이외)은 통과 — curl 확인과 장래의 서버 간 호출용.

본문 상한 1MB. 누구나 POST 할 수 있는 입구에 큰 본문을 던지지 못하게.

200 을 먼저 반환하고 처리는 뒤로 넘김:
  DB 와 프로필 조회를 기다렸다 응답하면 아침 혼잡 시간에 LINE 의 재전송이
  걸림. 실측 응답 1.3ms. 처리 실패는 재전송이 안 오므로 반드시 로그에 남김
  (push_logs 가 아니라 표준출력 — 아직 누구 것인지 모르는 단계의 실패도 있음).

예상 밖의 예외로 프로세스가 죽으면 cPanel 이 재기동할 때까지 webhook 이
전부 404 가 되므로, unhandledRejection / uncaughtException 을 잡아 두고
죽지 않게 함.


────────────────────────────────────────────────────────────────────────────────
  B-2.  서명 검증 (signature.mjs, 53행) — 시스템 전체의 경계
────────────────────────────────────────────────────────────────────────────────

webhook URL 은 공개돼 있어 누구나 POST 할 수 있습니다.
여기가 통과하면 이후는 전부 진짜로 취급하므로, 이 파일이 전체의 경계입니다.

  1) 생바이트(Buffer)로 HMAC-SHA256
     JSON.parse 한 것을 다시 JSON.stringify 하면 키 순서·공백·수치 서식에
     따라 다른 바이트열이 됨 → 올바른 요청까지 튕기거나, 반대로 우연히
     일치하는 서식이면 통과함. 어느 쪽이든 원인이 서명이라고 못 알아챔.
     app.mjs 에서 파싱은 검증 이후에만 일어나고, 검증도 그 순서를 봄.

  2) timingSafeEqual
     === 로 비교하면 몇 번째 글자에서 틀렸는지가 소요 시간에 드러남.
     길이가 다르면 예외 대신 false (base64 자릿수는 고정이라 정보가 안 샘).

  3) base64 (hex 아님)
     hex 로 비교하면 항상 불일치가 되어 "왜인지 전부 401" 이 됨.

  문자열로 넘기면 예외를 던져서 조용히 통과시키지 않음.


────────────────────────────────────────────────────────────────────────────────
  B-3.  이벤트 분배와 핸들러 4개
────────────────────────────────────────────────────────────────────────────────

webhook.mjs 는 events 배열을 직렬로 돕니다.
병렬로 하면 같은 사람의 follow 와 message 가 같은 편에 있을 때 순서가 뒤집혀,
아직 users 에 없는 사람에게 message 가 먼저 도착함.
하나가 실패해도 나머지는 처리하고, 실패는 결과에 섞어 반환.

재전송 대응 — 처리한 이벤트 목록 표를 만들지 않고 핸들러를 멱등하게 씀:

  이벤트     하는 일                                    멱등성 근거
  ---------  -----------------------------------------  ---------------------
  follow     users 확보 + 체험·진도 그릇 + 안내         insertNew 가 1062 버림
  unfollow   status='unfollowed'                        대입만 함
  message    상태질문 / 해지문의 / 시작안내 / 무응답    replyToken 이 1회성
  postback   이름·생년월일·코스·퀴즈 4분기              대입만 함
                                                        (코스는 IS NULL 조건부)

  목록 표를 두면 그걸 지우는 장치까지 필요해지므로,
  "몇 번 해도 같은 결과"로 충분한 동안은 부품이 적은 쪽이 나음.


▶ follow.mjs — 친구추가 / 블록

  · displayName 은 LINE 에서 가져오되, 못 가져와도 멈추지 않음
    (프로필 조회 1왕복이 5xx 였다고 친구추가 자체가 실패하는 건 수지가 안 맞음)
  · billing.startTrial + learning.ensureProgress 로 그릇 준비.
    둘 다 이미 있으면 아무것도 안 함 — 여기서 "다시 만들면" 블록→재추가마다
    체험이 연장되고 진도가 0으로 돌아감

  · 재추가 처리 (계획서를 그대로 따르면 깨지는 곳)
      계획서 5-1 은 "재추가 시 기존 유저 status 를 trial 로 갱신"이라고 되어
      있는데, 그대로 쓰면 101일치를 산 사람이 한 번 블록했다 돌아오면
      체험으로 떨어짐. 보유일수는 subscriptions 에 남아 있는데 발송만
      체험 취급이 되는, 고치기 어려운 고장.

      upsertOnFollow 는 status 를 안 건드리고, 호출부(follow.mjs:87)가
      결제 이력을 보고 정함:
        paid ? 'active' : 'trial'

      구매 후     status=active      days=104  current_day=42
      블록 후     status=unfollowed  days=104  current_day=42
      재추가 후   status=active      days=104  current_day=42   ← 유지

  · 회신은 이름 유무로 갈림
      이름 없음 → 강좌 설명 + 진단 페이지 안내.
                  이 강좌는 이름으로 진행되므로 이름이 들어올 때까지

                  갑자기 "이름을 등록해 주세요"만 도착함

    사람이 여기로 오는데, 그 사람에게 LINE 은 계속 무언이고 첫 메시지가
    다음 날 아침의 "1일차"였음 — 무엇에 등록했는지 모른 채 본문이 시작됨.

    LINE 이 webhook 실패로 보고 다시 걸어서 같은 처리가 여러 번 돎.

  · 블록(unfollow)은 지우지 않음. 지우면 재추가가 신규로 보여
    산 일수도 진도도 없던 일이 됨. 실제 삭제는 탈퇴 요구 때만(deleteUser).


▶ message.mjs — 이용자가 뭔가 보냄

  이 강좌는 "매일 아침 이쪽에서 보내는" 형태라 대화 응답은 상정하지 않지만,
  사람은 반드시 보냄 — "고마워" "해약하고 싶다" "지금 며칠째?"

  상태 질문   → 지금 N일째, 남은 M일 (형태소 분석 없이 단어 일치)
  중단 희망   → 블록 안내만
  시작 안내   → "코스"·"초급"·"이름" 등. 아직 안 정해진 것을 다시 꺼냄
  그 외       → 아무것도 안 함 (읽음 상태 그대로)

  시작 안내 경로를 연 이유:
    quickReply 버튼은 다음 메시지가 오면 못 누름. 배송 배치는 3회까지
    재촉하고 침묵하므로(ONBOARD_NOTICE_MAX), 침묵한 뒤에는 버튼만 남고
    누를 수가 없어 손이 끊김. 아직 안 정해진 것이 있으면 상태 질문보다
    이쪽을 우선함 — 0일째인 사람에게 "0일째까지 진행"이라고 답해도
    다음에 뭘 해야 할지 모름.

  "그 외"에 정형문을 안 보내는 이유: 매번 같은 답이 오면 알림만 늘고
  안 읽히게 됨. 아침저녁 2통이 본체이고 거기에 잡음을 섞고 싶지 않음.

  해지를 문면으로 처리하지 않는 이유:
    말투를 잘못 읽어 결제한 사람을 멈추면 안 됨.
    실제 중단은 사용자가 블록해서 unfollow 가 올 때만 일어남.

  LINE Developers 의 "검증" 버튼은 0 이 나열된 더미 replyToken 으로
  한 번 두드리므로, isVerifyToken() 으로 걸러 400 을 피함.


▶ postback.mjs — 버튼이 눌림

  data 는 이용자 단말을 경유해 돌아오는 문자열이라,
  우리가 보낸 것이 그대로 돌아온다는 보장이 없음(고칠 수 있음).

  · 정답 번호를 data 에 넣으면 안 됨 — 누르기 전에 고치면 반드시 정답이 됨.
    화면에는 "정답입니다"로만 보여서 아무도 눈치 못 챔
  · "30일차 퀴즈"라고 주장해도 quiz_checkpoints 표로 다시 확인
  · 정답은 서버에서만 조회

  받는 action 은 4개:

    action=name&use=web|line        어느 이름으로 부를까
    action=birth&ok=1|0             생년월일이 본인 것인가
    action=track&pick=beginner…     코스
    action=quiz&day=30&choice=2     절점 퀴즈

  · track 도 pick 값을 그대로 DB 에 안 넣음. repo 의 setTrack 이 ENUM
    3개와 대조 — ENUM 에 없는 값을 MySQL 에 넘기면 설정에 따라 예외가
    아니라 빈 문자열이 들어가고, 그 사람만 조용히 대상에서 빠짐
  · setTrack 은 track IS NULL 일 때만 씀. 연타·오래된 화면을 거슬러
    올라가 누른 두 번째는 claimed=false 로 돌아와 "이미 정해졌다"고 답함
  · 하나 답하면 그 자리에서 다음 질문을 회신. 안 하면 답했는데 아무 일도
    안 일어난 것처럼 보이고, 다음 버튼은 다음 날 아침까지 안 옴
  · 퀴즈 정답은 그 사람의 코스에서 조회 — 코스마다 원고가 다르므로,
    안 보고 초급으로 채점하면 중급인 사람이 받은 문제와 다른 답으로 매겨짐

  현재 content_templates 에 정답 컬럼이 없으므로 lookupAnswer 가 null 을
  반환하고, 핸들러는 "pending: 正答が未入稿です(P4)" 를 돌려줌.
  조용히 "오답"으로 만들지 않음 — 누른 사람에게는 이유가 안 보이므로.


────────────────────────────────────────────────────────────────────────────────
  B-4.  LINE Login 온보딩 (P3) + 시작 전 3가지 확인 (P5)
────────────────────────────────────────────────────────────────────────────────

점은 웹에서 먼저 끝납니다. 그 시점에 아는 건 이름과 생년월일뿐이고,
LINE 의 누구인지는 인증에서 돌아온 뒤에야 알 수 있습니다.
둘이 갖춰져야 어느 행에 쓸지 정해지므로, 먼저 온 쪽을 맡아 둡니다.

    1  POST /line/link/start
       사주 도착 → 형식 검사 → pending_links 에 예치
       → state + authorizeUrl 반환
            ↓ (브라우저가 LINE 인증 화면으로 나감)
    2  GET /line/callback?code=…&state=…
       state 로 예치물 회수(1회성)
       → code → accessToken → userId
       → users upsert → 이름·사주 기록 → 체험·진도 그릇 확보
       → Messaging API 로 getProfile 시도 → 친구 여부 판정 → 화면 분기

순서는 어느 쪽이든 됩니다. 친구추가가 먼저인 사람도, 연동이 먼저인 사람도
users 쓰기는 전부 upsertOnFollow 를 지나므로 두 명이 되지 않습니다.


■ state 보호 (token.mjs)

  생성      randomBytes(32) → base64url 43자. Math.random 아님
  저장      SHA-256 해시로만.
            생값이 새면 아직 안 넘어간 사주를 자기 LINE 에 붙일 수 있음
  사용      1회.
            UPDATE … WHERE consumed_at IS NULL AND expires_at > ?  가 이긴 쪽만
            (찾기 → 사용처리 2문으로 나누면 뒤로가기 연타 때 둘 다 통과)
  순서      consume 먼저, exchangeCode 나중.
            확인 전에 LINE 을 두드리면 무차별 대입의 상대를 대신 서 줌
  실패 문면 만료·재사용·형식오류를 전부 같은 화면으로.
            어디서 걸렸는지 알려주면 단서가 됨

■ 입력 검사 (link.mjs:54) — 자르기 전에 형식을 본다

  10자로 자른 뒤 검사하면
      "1995-04-12T23:00:00Z"  →  "1995-04-12"
  가 통과하는데, UTC 밤은 JST 로 다음날이라 일주가 하루 어긋난 사주가
  저장됨. 값은 "그럴듯한 날짜" 그대로라 나중에 대조해도 못 찾음.

  시각도 같은 이유로 안 자름 — "09:30:15+09:00" 를 잘라내면 시차를 떨군 채
  통과해 시주가 밀림.

  범위는 사이트(birth.js)와 같은 1930〜2030.
  여기를 넓게 잡으면 저장은 됐는데 사주가 안 서는 상태를 만들 수 있음.
  2월 30일 같은 날짜는 Date 왕복으로 걸러냄.
  rawResult 는 8KB 상한 — 무제한이면 이 입구가 보관소로 쓰일 수 있음.


■ 채널 프로바이더 불일치 감지

  Login 채널과 Messaging API 채널이 LINE Developers 의 같은 프로바이더에
  있지 않으면 돌아오는 userId 가 다른 값이 됩니다.
  그 userId 로 push 를 보내면 안 갑니다 —
  등록도 저장도 성공하고, 에러도 안 납니다. 발송이 시작되는 아침까지
  아무도 모릅니다.

  그래서 연동 완료 시점에 그 userId 를 Messaging API 쪽 getProfile 에
  넣어 봅니다:

      통과   → 이미 친구.       「連携が完了しました」
      404    → 아직 친구가 아님. 「あと一歩です」 + 친구추가 버튼
               (설치 직후 이게 반드시 404 라면 먼저 프로바이더를 의심할 것)
      403    → 보낼 수 없는 상태(블록 등)

  scope 는 profile 만 요구. openid 를 더하면 id_token 이 붙지만 userId 는
  profile 로 얻을 수 있음 — 안 쓰는 정보를 요구하면 동의 화면 항목이 늘어
  이탈이 늘어남.
  userId 를 id_token(JWT) 에서 안 꺼내는 이유도 같음: 서명 검증이 필요해지는데,
  이쪽은 자기가 친 TLS 연결로 자기 액세스 토큰을 붙여 묻는 것이라
  검증해야 할 제3자가 없음. 부품이 적은 쪽을 채택.
  다 쓴 액세스 토큰은 revoke (기다리지 않음. 실패해도 실해 없음).

■ schema.sql 을 고치지 않고 migrations/ 를 쌓는 이유

  schema.sql 은 CREATE TABLE IF NOT EXISTS 로 되어 있어 이미 데이터가
  들어있는 표에는 안 먹힘. 본번에는 이용자와 원고가 들어있으므로 추가는
  db/migrations/*.sql 쪽. migrate.mjs 가 schema.sql 뒤에 이름순으로 흘림.

  ALTER TABLE 에는 IF NOT EXISTS 가 없음(MariaDB 엔 있으나 MySQL 엔 없어
  양쪽에서 도는 표기가 안 됨). 그래서 "이미 걸려 있다"를 뜻하는 오류 번호만
  삼킴 — 1060(열 있음) 1061(인덱스 있음) 1068(PK 있음) 1091(지울 게 없음).
  전부 삼키면 철자를 틀린 ALTER 가 "적용 완료"로 조용히 지나감.

  "에러가 안 났다"는 증거가 안 되므로(삼킨 번호가 있으니), migrate.mjs 가
  information_schema 로 5개 열이 실제로 있는지 다시 셈.

■ 시각은 전부 JST (jst.mjs)

  빌린 서버의 시계가 JST 라는 보장이 없음(cPanel 공유 환경은 UTC 가 많음).
  DATETIME 은 시차를 갖지 않는 타입이라, 넣는 쪽과 읽는 쪽의 해석이
  어긋나면 아침 7시 발송이 정확히 그 창에 들어감.

      2026-08-02 21:55 UTC  =  2026-08-03 06:55 JST
                    ↑ UTC 로 날짜를 뽑으면 08-02. 매일 아침 어긋남

  방식: getTime() + 9h 후 getUTC* 로 읽음. 서버 TZ 설정에 안 기댐.
        (일본은 1951년을 마지막으로 서머타임이 없어 계속 UTC+9 고정)

  접속마다 SET time_zone = '+09:00' 도 실제로 내보냄 (db.mjs:86).
  mysql2 의 timezone 옵션은 드라이버 변환 설정이지 세션 시각이 아님:

      timezone 옵션만       @@session.time_zone=SYSTEM, NOW()=07:15 (UTC)
      SET time_zone 후      +09:00,                     NOW()=16:15 (JST)

  어긋나는 건 DEFAULT CURRENT_TIMESTAMP 컬럼(users.created_at /
  purchases.purchased_at / push_logs.sent_at)이고, 앱이 넣는 JST 와
  같은 표에 섞임. 섞인 뒤에는 어느 행이 어느 쪽이었는지 구별 불가.
  migrate.mjs 가 매번 이걸 다시 셈.

  날짜 범위는 BETWEEN 이나 DATE(sent_at)=? 가 아니라 반개구간:
    전자는 23:59:59.4 를 놓치고, 후자는 컬럼에 함수를 걸어 인덱스를 못 씀.

■ 왜 차입구(슬롯)를 조사별로 두었나

  한국어 조사는 직전 글자의 받침으로 형태가 바뀜:
      켄   (받침 있음) → 켄이에요 / 켄은 / 켄이 / 켄아
      아이 (받침 없음) → 아이예요 / 아이는 / 아이가 / 아이야

  {NAME}입니다 는 양쪽 다 되지만 {NAME}는 은 안 됨.
  원고 작성자에게 "받침 있는 이름에도 되는 문장만 써라"고 요구할 수 없으므로,
  조사마다 슬롯을 두고 고르는 건 렌더러의 일로 만듦.

  규칙은 사이트 본체(index.html 의 hasJong / ieyo / ega / fillName)에서
  옮긴 것. 따로 쓰면 같은 이름이 웹과 LINE 에서 다른 조사가 됨.
  실제로 사이트에서 한 번 "켄 씨은"을 낸 적이 있고, 이건 학습 콘텐츠로서
  틀린 것을 가르치는 것이 됨.

■ 슬롯 일람

    기본 3종 :  {NAME} 다나카     {OHAENG} 목      {ZODIAC} 돼지
    일본어   :  {NAME_JP} たなか  {OHAENG_JP} 木   {ZODIAC_JP} いのしし
    조사 6종 :  _IEYO  _EUN  _GA  _EUL  _WA  _VOC
                → 값째로 치환.  {NAME_EUN} → 아이는

  조사 슬롯은 값을 포함해 치환되므로 {NAME}{NAME_EUN} 은 "아이아이는"이 됨:

      {NAME}{NAME_EUN}       → 아이아이는       이중
      {NAME} 씨{NAME_EUN}    → 아이 씨아이는    이중 + 조사가 씨를 따라야 함
      {NAME_EUN}             → 아이는           이것이 올바름

  "씨"를 붙이고 싶은 날은 슬롯을 안 쓰고 "{NAME} 씨는"으로 직접 씀
  (씨는 모음 끝이라 값에 관계없이 는 으로 고정 가능).
  findMisplacedSlot() 이 정규식으로 이걸 검출.

  값이 필요한데 없으면 fillSlots 가 null 을 반환하고,
  여기서 기본값을 넣지 않음 — 넣으면 전원이 같은 이름·같은 오행이 됨.

  화자 라벨(who)만은 예외로 "あなた"를 넣음. 라벨은 배역이고 본문의
  "저는 ○○입니다"와는 다름. 안 넣으면 {NAME_JP} 9글자가 그대로 화면에 나옴.

■ 저녁은 아침의 재전송이 아님 (renderReview)

  같은 2통을 다시 보내면 알림만 1회 늘고 안 읽힘. 문제로 만들어 보냄.

    1통째  문법 이름 + 회화 1문(한국어만) + 단어(한글만)
    2통째  답

  · 회화는 1문만. 전부 내면 아침의 재전송이 됨.
    이름이 들어간 문장을 우선함 — 이 강좌에서 익히길 바라는 건
    "내 이름으로 말할 수 있는 형태"이므로. 없으면 첫 문장으로 충분
  · 2통으로 나누는 이유는 1통이면 같은 화면에 답이 나와 떠올릴 틈이 없음.
    pushMessage 가 배열을 받으므로 2통이어도 알림은 1회
  · 진도에 손대지 않음. 이 함수는 DB 를 모름 — 문자열만 만들게 해 두면
    손댈 방법 자체가 없음
  · 이름이 필요한데 없으면 null (아침과 같은 취급). 기본 이름을 안 넣음

  1문만 뽑으므로, 그 1문에만 문제가 있으면 아침은 통과하고 저녁이 무너짐.

  중복 검사는 코스 안에서 봄. 초급 1일차와 중급 1일차가 둘 다 있는 건
  정상이므로, 날짜 번호만으로 세면 2개 코스를 한 번에 입고할 때 전 날짜가
  "2번 나옵니다"가 되어 1건도 안 들어감.

    보내고 나서 진행하면, 송신은 성공했는데 진행에 실패한 날 같은 내용이

    두 번 가는 것보다는 가벼움(실패는 push_logs 에 남으므로 추적 가능).

  5를 8보다 먼저 하는 이유
    원고가 없는 날에 확보만 진행하면 아무도 안 읽은 날이 조용히 사라짐.
    중급·고급은 아직 미입고라 지금 실제로 여기에 걸림.

  4를 5보다 먼저 하는 이유
    이름과 코스는 정해지지 않으면 그날의 내용 자체를 만들 수 없음
    (이름은 회화문이 바뀌고, 코스는 뽑을 원고가 바뀜).
    정해지기 전에 진행하면 그날 내용이 빈 채로 사라짐 — 7-6 에서 이미
    한 번 저지른 실수와 같은 형태. 재촉은 3회까지(ONBOARD_NOTICE_MAX),
    그 뒤엔 침묵하되 진행은 멈춘 채라 나중에 답하면 그날부터 시작.
    생년월일 미확인은 여기서 안 멈춤 — 멈추는 건 운세뿐.

  이중 기동 방어

    advanceDay 의 "읽은 값 그대로면 바꾼다"로 막음.

  배치를 다시 걸었을 때 우리 쪽 기록이 남기 전에 죽었어도 LINE 쪽에서 걸러짐.

■ 이름이 없는 사람 처리

  처음엔 "등록 요청으로 갈아끼우고 날은 진행"이었음.
  101일이라는 수는 유지되지만, 진행한 날의 내용은 두 번 다시 안 감.
  1〜5일차는 전부 이름을 쓰므로 사이트를 안 거치고 친구추가만 한 사람은
  체험 3일간 본문을 한 번도 못 보고 끝남.

  지금은 진행하지 않음. 같은 날에 머무르고, 이름이 들어온 날 그날부터 시작.

  (pushlogs.countForDay 로 셈. 진행이 멈춰 있으므로 같은 날에 계속 걸림).

    빼고, 실패로도 남김("그날은 안 갔다"는 사실이므로)
  · 429 / 5xx / 408 만 재시도 (1→2→4초, Retry-After 가 있으면 그쪽 우선).
    4xx 를 재시도하면 문면 실수 하나로 레이트 리밋을 다 써서 그날 배송이
    전원 멈춤
  · PUSH_DISABLED=1 은 "송신만 정지"를 "확보도 안 함"으로 읽음 —
    멈춘 사이에 날짜만 진행돼 있으면 고친 뒤에 며칠분이 날아감
  · 1명이 예외로 죽어도 나머지는 배송 (선두 1명 때문에 전원이 못 받는 일 방지)
  · 200명씩 페이지네이션 — 인원이 늘었을 때 전원을 한 번에 메모리에 안 올림
  · 송신 실패가 나온 날은 exit 1 로 끝내 cron 실패 알림에 나오게 함
  · 직접 호출됐을 때만 main() 실행 — 검증이 읽어들이기만 해도 본번으로
    보내기 시작하는 일은 없어야 함

  옵션 (양쪽 공통):
    --dry-run           누구에게 무슨 날이 갈지만 출력
    --date=YYYY-MM-DD   그 날로 동작
    --limit=N           앞에서 N명만
    --not-before=7      일본 시간 7시 전이면 아무것도 안 함 (저녁은 18)

    0 * * * * /bin/bash ~/kstudy101-line/db/push-cron.sh evening >> ~/logs/push.log 2>&1

   전에 새 스크립트를 놓아도 아침 편이 멈추지 않도록 그렇게 해 둠.)

  스크립트 1본에 몰아둔 이유는 아래 nodevenv 탐색을 2곳에 두고 싶지 않아서.
  실제로 거기가 CloudLinux 의 activate 로 한 번 깨졌고, 고칠 곳이 2개면
  한쪽만 고쳐짐.

  철자가 틀린 인수는 조용히 아침으로 안 돌림 — 저녁 생각으로 쓴 행이
  매시 아침 편을 두드리게 됨.

■ cron 행에 명령을 직접 안 쓰는 이유

  쓰면 Node 버전이 행 안에 고정됨 (~/nodevenv/kstudy101-line/24/bin/node).
  cPanel 화면에서 버전을 올린 날 배송만 조용히 멈춤.
  멈춘 걸 알아챌 수 있는 건 받는 쪽뿐이고, 그 사람은 "오늘은 안 오네"라고만
  생각함.

■ push-cron.sh 가 하는 일

  · nodevenv/*/bin/activate 를 매번 탐색.
    sort -V | tail -1  (사전순이면 10 이 24 보다 뒤로 감)
  · CloudLinux 의 activate 가 미정의 CL_VIRTUAL_ENV 를 읽으므로,
    읽는 동안만 set +u.
    이건 cron 에서 부를 때만 나타남 — 배치 하견에서는 바깥 셸이 먼저
    activate 를 끝내 놔서 통과해 버림. "시험한 길"과 "본번에서 통하는 길"이
    달랐던 사례
  · 로그 5MB 초과 시 뒤쪽 1MB 만 남김
    (지우면 멈춰 있던 기간 자체를 알 수 없게 됨)
  · 추가 인수는 그대로 넘김 — --dry-run 을 붙여 부르면 cron 이 실제로 지나는
    길(activate 탐색·경로 조립)을 아무에게도 안 보내고 확인할 수 있음

■ 1시간마다 부르고 시각 판단은 Node 가 함

  공유 서버의 cron 은 서버 지방시로 도는데, 그 지방시가 무엇인지는
  빌린 쪽에서 확인하기 어렵고 이전·서머타임으로 조용히 어긋남.
  일본의 7시에 배송하고 싶은 것이지 이 기계의 7시가 아님.

  "7시 정각만"이 아니라 "7시 이후"인 이유는 7시 회차가 죽으면 8시 회차가
  줍기 위해서. 두 번 안 보내는 건 push_logs 의 sentToday 가 담당.

■ run.sh

  1. 송신처 확인 ($APP 없으면 중단 — "배치는 성공, 왜인지 안 돎"이 제일 읽기
     어려운 실패)
  2. 코드 배치 (위 4개 제외)
  3. 운세 엔진 복사 — saju.js / fortune.js / solar-terms.json → $APP/engine/
  4. npm install --omit=dev  (activate 는 sort -V 로 매번 탐색)
     — ci 가 아닌 이유: ci 는 node_modules 를 지우고 다시 만드는데, 여기서
       지워지는 것이 Selector 의 symlink 라서 가상환경과의 연결이 끊긴다
  5. migrate — 재기동보다 먼저. 여기서 실패하면 옛 코드가 계속 도는 편이
     새 코드가 옛 표에 대고 도는 것보다 안전
  6. content/ 가 있을 때만 seed-content
  7. 플래그 파일이 있을 때만 smoke / who / push --dry-run
  8. tmp/restart.txt touch — Passenger 는 돌고 있는 프로세스를 안고 있어
     놓기만 해서는 옛 코드가 계속 응답함

■ 플래그 3종

    ~/.run-smoke      실물 DB 로 한 바퀴
    ~/.run-who        배송 대상 상태 확인
    ~/.run-push-dry   배송 하견 (아무에게도 안 보냄)

  cPanel Fileman API 로 놓음 — SSH 없이도 신호를 보낼 수 있게.
  돌고 나면 스스로 지움.

  push 하견은 push-cron.sh 를 통해 부름 — push-daily.mjs 를 직접 부르면
  cron 이 지나는 길(activate 탐색)만 시험되지 않음.
