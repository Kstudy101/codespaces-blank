# 과금 계획서 — 3일 체험 후 구독

작성: 2026-08-03 / 선행: [plan-fortune-content.md](plan-fortune-content.md) §11.5 (「과금은 별도 계획서로」)

> 이 문서는 **계획**입니다. 승인 전까지 코드를 쓰지 않습니다.
> 과금은 되돌리기가 특히 어렵습니다 — 잘못 청구한 돈은 사과로 끝나지 않고,
> 일본의 정기구매는 표시 하나가 빠지면 **계약 취소권**이 생깁니다.

---

## 1. 조사 결과 — 지금 있는 것은 구독이 아닙니다

`server/lib/repo/billing.mjs` 와 스키마는 **선불 일수 패키지**로 되어 있습니다.

```js
export const PACKAGES = Object.freeze({
  "7days":   { days:   7, price:  980 },
  "14days":  { days:  14, price: 1680 },
  "30days":  { days:  30, price: 2980 },
  "60days":  { days:  60, price: 4980 },
  "101days": { days: 101, price: 7480 }
});
export const TRIAL_DAYS = 3;
```

| 있는 것 | 없는 것 |
|---|---|
| `subscriptions` 표 (이름만 구독) | 갱신 주기·다음 결제일·해지 예약 |
| `purchases` 표 (1회성 결제 이력) | 정기 결제 이력 |
| `creditPurchase()` — 재전송 무가산 | 갱신 시 일수 연장 |
| `payment_status` ENUM 5종 | `past_due`(결제 실패) 상태 |
| `.env` 의 `STRIPE_*` 자리 | 결제 경로 자체 (0줄) |
| `push_logs` 의 `upsell` 종별 | upsell 문면·발신 |
| — | **특정상거래법 표기 페이지** |
| — | **최종확인화면**(정기구매 필수) |

`subscriptions` 는 이름과 달리 **「총 며칠치를 샀는가」** 를 담는 표입니다
(`total_days_entitled`). 구독은 「지금 유효한가」이므로 **모델이 다릅니다.**

배포 배치도 이 전제 위에 있습니다.

```js
// server/db/push-daily.mjs
const entitled = Number(u.total_days_entitled) || 0;
if (next > entitled) return "日数切れ";
```

## 2. 먼저 정할 것 — 101일은 끝이 있는 강좌입니다

구독은 보통 **끝이 없는 서비스**에 씁니다. 이 상품은 101일에 끝납니다.
그래서 「3일 체험 후 구독」은 두 가지로 갈립니다.

### (가) 강좌 구독 — 101일을 다 받으면 자동 종료
```
체험 3일(무료) → 월 ○○엔 → 101일차 배포 후 자동 해지
                              (월 30일 배포 기준 약 3.4개월)
```
- 이용자에게 **끝이 보입니다.** 「언제까지 나가는지 모르는 결제」가 아님
- 일본에서 정기구매 불신의 가장 큰 원인이 「해지가 어렵다」인데, 이건 애초에 끝남
- 다만 **101일 뒤 매출이 0** 이 됩니다

### (나) 무기한 구독 — 101일 후에도 계속 (복습·신규 콘텐츠)
```
체험 3일(무료) → 월 ○○엔 → 계속 (101일 후는 복습/심화)
```
- 매출이 이어집니다
- 대신 **101일 이후에 보낼 것이 필요합니다.** 지금 0개이고,
  없는 채로 청구하면 그게 곧 문제가 됩니다

**(가)를 권합니다.** 지금 있는 것(101일)으로 성립하고, 나중에 (나)로
넓히는 것은 가능하지만 그 반대는 신뢰를 깎습니다. 「끝나는 강좌」로
팔아 두면, 이어서 낼 것이 생겼을 때 **새로 권하는 형태**가 됩니다.

## 3. 일본의 정기구매 규제 — 여기가 제일 무겁습니다

### 3.1 특정상거래법에 근거한 표기 (필수, 지금 없음)

유료로 파는 순간 **페이지 하나가 법적으로 필요**합니다.

| 항목 | 비고 |
|---|---|
| 사업자명 | **개인사업자면 본명** |
| 주소 | **개인사업자면 자택 주소일 수 있음** |
| 전화번호 | 연락 가능한 번호 |
| 판매가격 | 세금 포함 표시 |
| 대금 이외의 필요요금 | 통신료 등 |
| 지불 방법·시기 | |
| 역무의 제공시기 | 「신청 다음날 아침부터」 등 |
| 신청 철회·해제 | **해지 방법을 구체적으로** |

> ⚠️ **본명·주소·전화번호 공개가 필요합니다.** 법인이 아니면 개인 정보가
> 그대로 공개됩니다. 이건 코드로 못 푸는 문제이고, **착수 전에 확인해야 합니다.**
> 회피책으로 쓰이는 「청구가 있으면 지체 없이 개시」는 항목에 따라 인정 범위가
> 다르므로, 실제 운용은 확인이 필요합니다.

### 3.2 최종확인화면 (2022년 개정, 정기구매에 특히 엄격)

결제 직전 화면에 **한 화면에서 읽히도록** 넣어야 합니다.

- 분량 — 「101일간, 매일 아침 1회」
- 판매가격 — 월 ○○엔(세금 포함), **총액 얼마가 되는지**
- 지불 시기·방법 — 「매월 ○일에 자동 결제」
- 인도 시기 — 「결제 다음날 아침부터」
- **해지 방법** — 「LINE 에서 〈해지〉라고 보내면 즉시」 같은 구체적 문구
- 갱신 주기 — 「1개월마다 자동 갱신」

빠지면 **취소·무효 주장이 가능**합니다. 「작게 써 두었다」는 통하지 않습니다.

### 3.3 그래서 결제 화면은 어디에 두는가

Stripe Checkout(호스팅 결제 페이지)을 쓰면 **카드 번호가 우리 쪽을 지나지 않습니다.**
지금 privacy.html 이 「クレジットカードの番号を当方が受け取ることはありません」라고
이미 적었으므로, 이 방식이 그 문장을 참으로 유지합니다.

다만 **최종확인화면은 Stripe 의 기본 화면만으로는 위 항목을 못 채웁니다.**
→ 우리 쪽에 확인 페이지를 두고, 동의 후 Stripe 로 넘기는 구조가 필요합니다.

```
LINE「続ける」 → api.kstudy101.jp/checkout?token=… (최종확인화면)
              → Stripe Checkout (카드 입력)
              → Stripe webhook → 서버가 갱신
              → LINE 으로 완료 통지
```

## 4. 스키마 변경

`subscriptions` 에 더합니다(기존 열은 지우지 않습니다 — 선불 이력이 남아 있음).

```sql
ALTER TABLE subscriptions
  ADD COLUMN stripe_customer_id     VARCHAR(64) NULL,
  ADD COLUMN stripe_subscription_id VARCHAR(64) NULL,
  ADD COLUMN current_period_end     DATETIME NULL,   -- 다음 결제일
  ADD COLUMN cancel_at_period_end   BOOLEAN NOT NULL DEFAULT 0,
  ADD UNIQUE KEY uq_stripe_sub (stripe_subscription_id);
```

`payment_status` ENUM 에 **`past_due` 추가**. 결제 실패는 「해지」와 다릅니다 —
카드 만료로 하루 실패한 사람을 즉시 끊으면, 고칠 기회를 주기 전에 끊는 것이 됩니다.

```
none → trial → paid ⇄ past_due → expired
                  ↘ refunded
```

**결제 이력은 `purchases` 에 계속 넣습니다.** `package_type` ENUM 에
`subscription` 을 더하고, `payment_ref` 에 Stripe 의 invoice id 를 넣습니다.
`creditPurchase()` 의 **재전송 무가산**(1062 로 판정)이 그대로 쓰입니다 ──
Stripe webhook 은 같은 이벤트를 여러 번 보냅니다.

## 5. 배포 배치가 바뀌는 곳

지금:
```js
const entitled = Number(u.total_days_entitled) || 0;
if (next > entitled) return "日数切れ";
```

구독에서는 **「오늘 유효한가」** 로 바뀝니다.

```
payment_status = 'trial'    → trial_end 까지
payment_status = 'paid'     → current_period_end 까지
payment_status = 'past_due' → 유예 ○일까지 (아래 결정 필요)
그 외                        → 보내지 않고 upsell 대상
```

`listDeliverable()` 의 `WHERE u.status IN ('trial','active')` 도 함께 봅니다.

**결정 필요** — `past_due` 유예 기간. 0일이면 카드 만료로 즉시 끊기고,
길면 무료로 계속 받습니다. **3일**을 제안합니다(Stripe 의 재시도 주기와 맞음).

## 6. 해지

일본의 정기구매에서 **해지가 어렵다는 인상이 가장 큰 위험**입니다.

- **LINE 에서 「해지」로 즉시** — 웹훅이 이미 문자를 받고 있으므로 붙일 수 있습니다
- 해지해도 **이미 낸 기간 끝까지는 배포**(`cancel_at_period_end`)
- 해지 시 「○월 ○일까지는 계속 받으실 수 있습니다」를 반드시 회신
- 환불 규정을 특정상거래법 표기에 명시 (일수 비례? 무환불?) — **결정 필요**

## 7. 체험 3일에서 구독으로 넘기는 지점

```
1일차  배포
2일차  배포
3일차  배포 + 「내일부터는…」 안내 (여기가 upsell)
4일차  결제 있으면 배포 / 없으면 upsell 1회, 이후 침묵
```

**침묵을 넣는 이유** — 결제하지 않은 사람에게 계속 권하면 차단당합니다.
차단은 되돌릴 수 없고, 나중에 낼 것이 생겨도 닿지 않습니다.
`push_logs` 에 `upsell` 종별이 이미 있으므로 **몇 번 보냈는지 셀 수 있습니다.**

**결정 필요** — upsell 최대 횟수. **2회**(3일차 + 7일 후)를 제안합니다.

## 8. 결정이 필요한 것 (착수 전)

| # | 항목 | 제안 |
|---|---|---|
| ① | 구독 모델 | **(가) 101일 완료 시 자동 종료** |
| ② | 가격 | 미정 — 월 얼마 / 총액이 얼마로 보이는지 |
| ③ | 기존 선불 패키지 | 미정 — 없애면 코드가 하나, 병행하면 두 갈래 |
| ④ | 결제 사업자 | **Stripe** (`.env` 에 자리 있음, Checkout 로 카드 미접촉) |
| ⑤ | **특정상거래법 표기의 본명·주소** | **미정 — 코드로 못 푸는 문제. 확인 필요** |
| ⑥ | `past_due` 유예 | **3일** |
| ⑦ | 환불 규정 | 미정 — 표기에 명시해야 함 |
| ⑧ | upsell 횟수 | **2회** (3일차 + 7일 후) |

**⑤ 가 정해지지 않으면 유료화 자체를 시작할 수 없습니다.**

## 9. 착수 순서

```
1. ①②③④⑤⑦⑧ 결정
2. 특정상거래법 표기 페이지 + 최종확인화면 문안      ← 법적 요건이 형식을 정함
3. 스키마 (ALTER + payment_status 확장) + 검증
4. Stripe Checkout + webhook + 재전송 무가산 검증
5. 배포 배치의 「유효한가」 판정 교체 + 검증
6. 해지(LINE 문자) + 회신 문안
7. upsell 문면 (P4-c 와 함께)
8. 테스트 모드로 전 경로 1회 + 실카드 1회
```

> **2 를 3보다 먼저** 두는 이유 — 표기해야 하는 항목이 화면과 데이터 구조를
> 정합니다. 코드를 먼저 쓰면, 표시 의무를 채우려고 나중에 다시 고칩니다.
