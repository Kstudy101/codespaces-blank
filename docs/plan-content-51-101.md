### 1-2 「값 3 개」가 아니라 코드 관문은 4 개입니다

STATUS.md §3 은 `TOKUSHOHO_URL` / `REFUND_POLICY` / `RICHMENU_IMAGE` 를 듭니다.
그러나 가격표를 여는 관문(`missingLegalConfig()`)이 실제로 보는 것은:

```
TOKUSHOHO_URL · REFUND_POLICY · STRIPE_SECRET_KEY · STRIPE_WEBHOOK_SECRET
```

`RICHMENU_IMAGE` 는 이 관문에 **없습니다**(리치메뉴는 별개). 대신 Stripe 키 2 개가 있습니다.
즉 원고를 60 일까지 채워도, **이 4 개가 비어 있으면 가격표는 여전히 안 나옵니다.**

## 2. §1 대조표

### 2-1 무엇을 근거로 만들었고, 무엇이 한계인가

지시서 §1-1 은 이 SQL 을 요구합니다.

```sql
SELECT day_number, grammar_point
  FROM content_templates
 WHERE track = 'beginner'
 ORDER BY day_number;
```

**이 기기에서는 실행할 수 없습니다.** 본번 DB 접속정보는 저장소에도 `.env` 에도 없고,
cPanel → Setup Node.js App → Environment variables 가 유일한 출처입니다(STATUS §5).
`server/content/`(실원고)도 서버 위에만 있습니다.

그래서 **저장소 안의 정본 기록**으로 대조표를 만들었습니다 —
[docs/plan-p4-content.md](plan-p4-content.md) §7-4(1~30 일차 입고 결과)와 §7-7(31~50 일차 입고 결과)입니다.
이 두 절은 실제 입고를 마치고 **그 날 무엇을 넣었는지 일차별로 적어 둔 기록**이라, 커리큘럼 대조에는 충분합니다.

**한계 하나만 분명히 해 둡니다.** 이 기록은 「30 일차 = 반말 + 이름 부르기」처럼 **요지**로 적혀 있고,
DB 의 `grammar_point` **문자열 그대로**는 아닙니다. 따라서:

- **어느 커리큘럼 항목이 쓰였나** — 이 표로 판단할 수 있습니다 (아래 §2-3, §2-5)
- **문자열 중복 여부** — 이 표로는 못 봅니다. 기계가 봐야 합니다 (§5-3, §7-2)

대표님이 위 SQL 을 한 번 실행해 결과를 주시면 §2-4 의 「확인 필요 6 건」이 확정되고,
그것으로 §3 의 배정안이 그대로 확정되거나 §3-6 의 교체 규칙이 발동합니다.

## 3. 51~101 배정안 (51 일)

### 3-1 배정 원칙

1. **§2-5 의 미사용 62 항목에서만** 뽑았습니다 (지시서 §1-1·§7)

## 5. ★ 집필 전에 젬에게 전달할 것 — 지시서에 없는 함정 3 건

전부 **실제로 돌려서** 확인했습니다.

### 5-1 `grammar_tip_kr` 에는 이름 슬롯을 쓸 수 없습니다

지시서 §2-1 은 `requires_name_slot` 을 「**본문과 tip 의** 실제 `{NAME` 사용과 일치해야 함」이라고 적어,
tip 에도 슬롯을 써도 되는 것처럼 읽힙니다. **쓰면 그 날이 통째로 거부됩니다.**

`render.mjs` 의 `renderDay()` 는 tip 을 그대로 붙일 뿐 `fillSlots()` 를 통과시키지 않습니다:

```js
if (template.grammar_point)  head.push(`【今日の文法】${template.grammar_point}`);
if (template.grammar_tip_kr) head.push(template.grammar_tip_kr);   // ← 치환 없음
```

`grammar_tip_kr` 에 `{NAME_EUN}` 을 넣고 `--check` 를 돌린 실제 출력:

```
✗ 4 件あります。1 件も入れていません。
  ・beginner 51日目: 켄 の朝で差し込み口が残っています: {NAME_EUN}
  ・beginner 51日目: 켄 の夕で差し込み口が残っています: {NAME_EUN}
  ・beginner 51日目: 사쿠라 の朝で差し込み口が残っています: {NAME_EUN}
  ・beginner 51日目: 사쿠라 の夕で差し込み口が残っています: {NAME_EUN}
```

**관문이 막아주므로 사고는 안 납니다.** 다만 메시지가 「어느 칸인지」를 말하지 않아,
51 일분을 그렇게 써 놓고 나서야 알게 되면 51 일분을 고칩니다.

> **해소됨 (2026-08-07, §6-6).** 이제 첫 줄에 欄 이름이 나옵니다 —
> `grammar_tip_kr に差し込み口は使えません（説明は全員に同じ文面で届きます）`

→ **규칙: 이름 슬롯은 `dialogue_template` 의 `kr` / `ja` / `who` 에만.**

### 5-2 ★★ `{OHAENG}`·`{ZODIAC}` 은 관문이 통과시켰습니다

> **해소됨 (2026-08-07, §6-6).** 아래는 승인을 받기 위해 제시한 **수정 전**의 실측입니다.
> 지금은 「사주 없는 이용자」 픽스처가 입고 전에 막습니다.

지시서 §3-2·§7 이 금지하지만, **기계는 안 막았습니다.** 실측:

```
probe-ohaeng.json — 1 日ぶん → beginner
検査します
  ✓ 1 日ぶん、問題なし          ← {OHAENG_GA} 와 {ZODIAC_WA} 를 쓴 날이 통과
```

`content-check.mjs` 의 검사용 이용자(`PROBES`) 2 명이 **둘 다 오행·띠를 갖고 있기** 때문입니다.
실제 이용자에는 안 가진 사람이 있습니다 — `onboarding.mjs` 는 `ohaeng_main` 의 **부재**를
「사이트 진단을 안 거친 사람」의 판별자로 쓰므로, **LINE 에서 바로 친구추가한 사람은 영원히 빕니다.**

같은 원고를 두 이용자에게 실제로 렌더한 결과:

```
== 사이트 경유 ==
  📚 53日目
  【今日の文法】-와 / -과 · -하고 · -(이)랑
  けん：켄은 목이 좋아요.
  …
== LINE 직접 ==
  renderDay → null
```

**`null` 의 뒤가 문제입니다.** `push-daily.mjs` 는 이것을 「이름이 없는 사람」으로 처리합니다:

- **날을 진행하지 않습니다** (같은 날에 머무름)
- 「お名前を登録してください」를 **2 회** 보내고, 그다음부터 **침묵**합니다
- 그런데 그 사람은 **이름이 이미 있습니다.** 안내대로 해도 아무것도 안 바뀝니다
- 오행은 사이트 진단으로만 들어오는데, 안내는 그 말을 하지 않습니다

→ **막다른 골목입니다.** 그 사람의 강좌는 그 날에서 영구히 멈추고, 본인은 빠져나올 방법이 없습니다.
문의가 오기 전까지 아무도 모릅니다(발신 실패가 아니라 「정상적으로 안내를 보낸 상태」이므로).

**§6 의 검증 도구는 정확히 이것을 막기 위한 것입니다.**

### 5-3 1~50 일차와 같은 `grammar_point` 를 파일 단위 검사로는 못 잡습니다

`content-check.mjs` 의 중복 검사는 **그 실행에 넘어온 날들 안에서만** 봅니다:

```js
const points = new Map();
for (const d of days) {              // ← days = 이번에 넘긴 파일들뿐
  ...
  if (points.has(k)) problems.push(`… ${points.get(k)}日目と同じ文法「${p}」`);
}
```

지시서 §5 절차 3 번은 파일을 **지정해서** 부르므로(`--check content/beginner-51-60.json`),
**DB 에 이미 들어 있는 1~50 일차는 비교 대상에 없습니다.**
→ 해결책은 코드가 아니라 절차입니다. §7-2 를 보십시오.

## 6. 검증 도구 — **구현 완료 (2026-08-07 대표 승인)**

> 아래 §6-1~6-5 는 승인받은 계획 원문이고, **결과와 승인 후 늘어난 범위는 §6-6** 에 있습니다.

### 6-1 접근 방식

§5-2 의 막다른 골목을 **원고가 서버에 들어가기 전에** 세웁니다.
새 도구를 만들지 않고, **`content-check.mjs` 의 `PROBES` 에 이용자 1 명을 더합니다.**

지금 `PROBES` 는 「받침 있는 이름 / 없는 이름」 2 명이고, 둘 다 오행·띠를 갖고 있습니다.
여기에 **「이름은 있고 사주는 없는 사람」**(＝LINE 직접 유입자)을 넣으면,
기존 검사 루프가 그대로 그 사람으로도 조립해 보고 `null` 이면 잡습니다.

**이 방식을 권하는 이유** — 「초급에서 오행 금지」라는 **규칙을 새로 만들지 않습니다.**
지키려는 것은 규칙이 아니라 사실입니다: **오행 없이 못 읽는 날은 그 사람에게 막다른 골목이다.**
그래서 중급·상급에도 자동으로 같이 걸립니다. 슬롯 이름 목록을 관리할 필요도 없습니다.

### 6-2 코드 스니펫

**`server/lib/content-check.mjs`** — `PROBES` 에 1 명 추가:

```js
const PROBES = [
  { name_kr: "켄", name_reading: "けん",
    ohaeng_main: "목", raw_result_json: { zodiac: "닭" } },      /* 받침あり */
  { name_kr: "사쿠라", name_reading: "さくら",
    ohaeng_main: "화", raw_result_json: { zodiac: "돼지" } },     /* 받침なし */

  /* LINE から直接友だち追加した人。名前はあるが四柱は**永久に**空 ──
     onboarding.mjs が ohaeng_main の不在を「サイト診断を通っていない」の
     判別に使っているので、この人に四柱が入る道は無い。
     この人で組み立てられない日は、その人の講座がそこで永久に止まる
     （push-daily は「名前が無い」と読んで日を進めず、2 回促して黙る）。 */
  { name_kr: "유이", name_reading: "ゆい",
    ohaeng_main: null, raw_result_json: {} }
];
```

`checkDay()` 의 조립 루프는 **그대로**입니다 — `PROBES` 를 도는 형태라 자동으로 3 명이 됩니다.
다만 실패 메시지가 「組み立てられませんでした」로만 나오면 원인을 모르므로, 한 줄만 손봅니다:

```js
      if (!msgs) {
        /* 名前はあるのに組めない ＝ 名前以外の差し込み口（四柱）を使っている。
           この人には入る道が無いので、その日は永久に止まる。 */
        const why = probe.ohaeng_main ? "" :
          "（{OHAENG}/{ZODIAC} を使っていませんか ── LINE 直接の方には値がありません）";
        at(`${probe.name_kr} の${label}で組み立てられませんでした${why}`);
        continue;
      }
```

### 6-3 수정될 파일 경로

```
server/lib/content-check.mjs     PROBES 에 1 명 + 실패 메시지 1 줄
tools/verify-render.mjs          「사주 없는 사람으로 조립 실패를 잡는다」 단정 2 건 추가
```

**그 외에는 손대지 않습니다.** `render.mjs` 도 `seed-content.mjs` 도 바뀌지 않습니다.

### 6-4 트레이드오프

| | |
|---|---|
| **얻는 것** | §5-2 의 막다른 골목이 입고 전에 잡힘. 중급·상급에도 자동 적용. 슬롯 목록 관리 불필요 |
| **잃는 것** | 앞으로 **사주를 본문에 쓰는 날을 만들 수 없습니다.** 지금은 어차피 못 만들지만(막다른 골목이므로), 나중에 「사이트 경유자에게만 다른 원고」를 하려면 이 관문을 먼저 풀어야 합니다 |
| **대안 (나)** | `{OHAENG`·`{ZODIAC` 문자열을 금지 목록으로 거부. 더 단순하지만 **규칙이 하나 늘고**, 「왜 안 되는가」가 코드에서 사라집니다. 권하지 않습니다 |
| **대안 (다)** | 아무것도 안 하고 지시서 §7 의 금지에 맡김. **51 일 × 사람이 지키는 규칙**이라, 한 번 새면 문의가 올 때까지 모릅니다 |

### 6-5 제외 (scope 밖)

- `grammar_tip_kr` 을 `fillSlots` 에 통과시키는 것 — **하지 않습니다.** 지금 관문이 막고 있고,
  통과시키면 tip 이 사람마다 달라져 「같은 설명을 다시 읽는다」가 깨집니다. §5-1 은 **문서로** 전달합니다
- 1~50 일차 원고 수정 — 지시서 §10
- 중급·상급 — 지시서 §10
- 퀴즈 백필 — §4-3 의 ③

server/db/seed-content.mjs     머리말에 2 단계 검사 절차 등록 (지침 3 번. 동작은 안 바뀜)
```

실측 — 사주 슬롯을 쓴 원고를 넣어 본 출력입니다:

✗ 2 件あります。1 件も入れていません。
  ・beginner 53日目: 유이 の朝で組み立てられませんでした
    （{OHAENG}/{ZODIAC} を使っていませんか ── LINE から直接来た方には値がありません）
  ・beginner 53日目: 유이 の夕で組み立てられませんでした（同上）
```

같은 실행에서 **이름만 쓰는 정상 원고는 그대로 통과**합니다(거짓 양성 없음 — 단정으로도 고정).

### 6-7 ★ 대표님께 — 이 관문이 1~50 일차를 걸 수 있습니다

`content-check` 는 **입고할 때만** 돕니다. 이미 DB 에 있는 1~50 일차는 다시 검사받지 않습니다.
그런데 §7-2 의 **② (인자 없이 `--check`)** 는 `content/` 전량을 읽으므로 **1~50 일차도 함께 검사합니다.**

→ **② 를 처음 돌릴 때 1~50 일차에서 걸릴 가능성이 있습니다.**

걸린다면 그것은 관문의 오작동이 아니라 **진짜 문제**입니다 —
그 날 이후로 LINE 직접 가입자의 강좌가 이미 멈춰 있다는 뜻이고, 지금은 아무 신호도 안 납니다.
`server/content/` 가 서버 위에만 있어 이 기기에서는 확인할 수 없습니다.

**②가 1~50 일차에서 걸리면 51~60 입고를 멈추지 마시고, 걸린 일차 번호만 알려주십시오.**
지시서 §10 이 「1~50 일차 원고는 고치지 않습니다」라고 그어 둔 선이라, 별건으로 판단하실 일입니다.
(참고: 51~60 만 넣는 ①은 이 영향을 받지 않습니다)

## 7. 검증 절차 보완 — 지시서 §5 에 한 줄

### 7-1 좋은 소식 — 업로드 **전에** 로컬에서 전부 잡을 수 있습니다

`seed-content.mjs --check` 는 **DB 도 `npm install` 도 필요 없습니다.**
`--check` 분기가 `getPool()` **앞에서** 끝나고, `db.mjs` 는 `mysql2` 를 함수 안에서 동적으로만 읽기 때문입니다.

이 Windows 기기에서 실제로 확인했습니다:

```
> node db/seed-content.mjs --check <파일>
原稿を読みます
  probe-51-52.json — 2 日ぶん → beginner
検査します
  ✓ 2 日ぶん、問題なし
クイズの答え合わせ（1 問 ── 添字を解いた文字列で確かめてください）
  [beginner day 51] 「わたしもコーヒーが好きです」は？ → answer:1 = 「저도 커피를 좋아해요」
--check なので、ここで終わります
EXIT=0
```

→ **젬이 원고를 넘기기 전에 스스로 돌릴 수 있습니다.** 형식 문제로 왕복하는 횟수가 줄어듭니다.
필요한 것은 `server/` 폴더와 Node 뿐입니다(원고 파일 경로를 인자로 주면 `content/` 도 필요 없음).

### 7-2 ★ 지시서 §5 의 3 번을 **두 번** 부르십시오

```bash
# ① 지금 지시서대로 — 그 파일만 본다
node db/with-env.mjs db/seed-content.mjs --check content/beginner-51-60.json

# ② 추가 — 인자 없이. content/ 전량을 한 번에 검사한다
node db/with-env.mjs db/seed-content.mjs --check
```

②가 필요한 이유는 §5-3 입니다. **인자 없이 부르면** `load()` 가 `content/` 를 통째로 읽어
1~50 일차와 새 51~60 일차를 **같은 검사에** 넣으므로:

- **1~50 일차와 같은 `grammar_point` 를 쓴 날**을 잡습니다 (§5-3 이 못 잡던 것)
- 결번도 함께 보입니다

②도 `--check` 이므로 **아무것도 쓰지 않습니다.** ①이 0 건이어도 ②가 0 건이 아니면 투입하지 마십시오.

### 7-3 문자 깨짐 (지시서 §5-1)

지시서의 `head -c 400` 은 파일 앞 400 바이트만 봅니다. **오답 선택지는 대개 뒤에 있습니다** —
지시서 §5-1 이 지적한 과거 사고가 정확히 그 지점이었습니다. `--check` 의
「クイズの答え合わせ」 출력이 **정답 문자열을 해석해서** 보여주므로(위 §7-1 출력),
그 줄이 읽히면 최소한 정답 쪽은 안전합니다. 오답 선택지는 여전히 눈으로 보셔야 합니다.

### 8-1 젬에게 그대로 넘길 규칙 (관문이 강제하는 것)

집필 지침에 이 4 줄을 넣어 주십시오. 전부 **기계가 막으므로** 어기면 그 날이 입고되지 않습니다.

1. 이름 슬롯은 **`dialogue_template` 의 `kr` / `ja` / `who` 에만.**
   `grammar_tip_kr` · `vocab_3` · `fortune_bridge` · `quiz` 에는 못 씁니다
2. **`{OHAENG}` · `{ZODIAC}` 계열 16 종은 쓸 수 없습니다** (LINE 직접 가입자에게 값이 없음)
3. 일본어 줄(`ja`)에는 `{NAME_JP}` 만, 한국어 줄(`kr`)에는 `{NAME_JP}` 금지
4. 조사는 슬롯 하나로 (`{NAME_EUN}`). `{NAME}{NAME_EUN}` 도 `{NAME}은/는` 도 안 됩니다

집필 중에 스스로 확인하는 법 — **DB 도 `npm install` 도 필요 없습니다** (§7-1):

```bash
node db/seed-content.mjs --check <원고.json>
```
