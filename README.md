# 名前で学ぶ韓国語 (이름으로 배우는 한국어)

> 당신의 이름이 첫 번째 한국어 교재입니다.

일본인 사용자가 **자기 이름**을 입력하면, 그 이름을 재료로 한국어를 배우는 웹 서비스.
"운세"가 입구가 되고 **한국어 교육이 본 서비스**가 되는 구조입니다.

진단 로직은 전부 브라우저 안에서 끝납니다. 서버·빌드·API 키가 필요 없습니다.
(외부 요청은 Google AdSense·애널리틱스뿐입니다 — 아래 [개인정보와 광고](#개인정보와-광고) 참고.)

### `index.html` 의 「자체 완결」은 이제 깨졌습니다

원래 `index.html`은 CSS·JS를 전부 인라인해 **파일 하나로 어디든 던져놓으면 동작**하는
상태였습니다. 운세 기능을 넣으면서 그 성질을 버렸습니다.

```html
<script src="/saju.js"></script>      <!-- 사주 계산 -->
<script src="/fortune.js"></script>   <!-- 점수 -->
<script src="/study.js"></script>     <!-- 단어장·출석 -->
<script src="/omikuji.js"></script>   <!-- 「오늘 아직 안 뽑은 것」 표시 -->
```

**의도적인 결정입니다.** `saju.js` 는 `index`·`gilbang`·`amulet` 3장이,
`study.js` 는 `index`·`words`·`omikuji`·`amulet` 4장이 씁니다. 같은 계산을 페이지마다
복붙하면 반드시 한쪽만 고치게 되고, `page.css` 를 여러 장이 공유하는 것과 같은
이유입니다. 어차피 AdSense·GA·Clarity·`kanji.json` 으로 외부 의존은 이미 있었습니다.

**대신 잃은 것을 적어 둡니다** — `index.html`을 `file://` 로 바로 열면 운세 부분이
동작하지 않습니다. 로컬에서는 아래 「로컬 실행」의 HTTP 서버를 써야 합니다.

`page.css`의 컬러 토큰을 `index.html`과 맞추는 일은 남아 있지만, **손으로 지키는
약속에서 빌드가 막는 것으로 바꿨습니다.** 실제로 `--gold`를 옮겨 적지 않아
`/gilbang` 방위반에서 「중앙」을 가리키는 점이 사라져 있었습니다 —
`background`는 상속되지 않으므로 정의되지 않은 `var()`는 투명이 되고,
중앙이 나오는 사람에게만 아무것도 안 보이므로 화면을 봐도 알 수 없습니다.
`build-site.sh` 가 두 방향으로 봅니다.

| 검사 | 잡는 것 |
|---|---|
| 폴백 없는 `var(--x)` 가 어디에도 정의되지 않음 | 옮겨 적기를 빠뜨림 (`--gold` 가 이 경우) |
| 양쪽에 다 있는데 **값이 다름** | 한쪽만 색을 바꿈 |

**캐시도 같은 이유로 손봤습니다.** `.htaccess` 는 외부 JS가 하나도 없던 시절에 쓴
것이라 기본값이 1주일이었는데, 공용 스크립트는 파일명에 **버전이 없습니다.**
HTML은 매번 다시 받고 JS는 최대 1주일 낡은 채로 남으면, 「새 HTML이 옛 JS를 부르는」
조합이 생깁니다 — 고친 줄 알았던 문제가 일부 이용자에게만 남고, 그 사람에게만 재현됩니다.
`.js` 를 HTML과 같은 `no-cache, must-revalidate` 로 바꿨습니다. `no-cache` 는
「저장하지 마라」가 아니라 「쓰기 전에 확인해라」이므로, 안 바뀌었으면 304만 돌아옵니다.
배포 워크플로가 **실제로 돌아오는 헤더**를 확인합니다.

### 깨알 지식(豆知識) 늘리는 법

`tips.html` 에 `<article class="tip">` 을 복사해 추가하면 끝입니다.
스타일은 `page.css` 의 `.tip` 컴포넌트가 담당하므로 CSS 수정이 필요 없습니다.

```html
<article class="tip">
  <div class="tip-badge">
    <span class="tip-ja">豆知識<small>まめちしき</small></span>
    <span class="tip-ko">깨알 지식 ⑥</span>
  </div>
  <h2>제목</h2>
  <p>본문</p>
</article>
```

**index.html 에는 본문을 복사하지 말 것.** 같은 글이 두 URL 에 있으면 AdSense 의
「コンテンツが複製されている」 반려 사유가 됩니다. 최상단 `.tipbar` 는 링크만 겁니다.

## 구조

| STEP | 내용 | 학습 요소 |
|---|---|---|
| 1 | 내 이름의 한글 표기 + 한국 한자음 | 한글 표기, 한자음 차이 |
| 2 | 내 이름으로 한글 자모 분해 | 자음 + 모음 조립 원리 |
| 3 | 이름 한자의 한국어 단어와 예문 | 어휘 |
| 4 | 내 이름이 들어간 문장 만들기 + **장면 회화**(접힘) | 문형 + 조사 + 회화 |
| 5 | 한국에서의 호칭 (씨 / 님 / 아·야) | 호칭 문화 |
| — | **게이트**: 생년월일 입력 유도 | 무료 → 추가 정보 |
| 6 | 한국식 성명학(자음 오행) + 띠 + 생년월일 말하기 | 문화 + 숫자 |
| — | 「오늘 배운 한국어」 정리 | 복습 |
| — | **SNS 공유** (카드 이미지 + 각 SNS) | 바이럴 |

**2단계 설계 의도** — 처음부터 이름 + 생년월일을 요구하지 않습니다.
이름만으로 무료 결과를 먼저 경험시킨 뒤 생년월일을 요청해, 심리적 진입장벽을 낮춥니다.

### 매일 돌아오게 만드는 고리 (STEP 과는 별개)

이름 진단은 **한 번 하면 끝**입니다. 그래서 페이지 상단에 매일 달라지는 것을 두고,
거기서 다른 페이지로 보냅니다. 자세한 근거는 `docs/plan-fortune-content.md` §7.

```
① 홈 상단 「오늘의 운세」  생년월일 입력 → 6항목 점수 + 전회 대비 증감
        ↓
② 「오늘의 3어」          운세 항목에 맞춰 3장. 발음 재생 · 단어장 저장
        ↓
③ 출석 스탬프             「N일 연속」. 운세를 본 시점에 찍힘
        ↓
④ 결과에 따라 분기         금운 낮음 → /amulet · 사업운 높음 → /gilbang
                          아직 안 뽑았으면 → /omikuji
```

**④ 를 1본만 내는 것이 핵심입니다.** 전원에게 같은 링크를 늘어놓으면 그냥 메뉴이고,
두 개를 동시에 내도 메뉴로 돌아갑니다. 실측 출현율은 부적 28.9% / 길방 12.4% /
아무것도 안 냄 58.7% 로, **절반 이상은 아무것도 나오지 않는 쪽이 정상**입니다.

바뀌는 주기를 페이지마다 일부러 다르게 두었습니다.

| | 오늘의 운세 | 오미쿠지 | 길방 | 부적 |
|---|---|---|---|---|
| 근거 | 사주 × 일진 (결정론) | 난수 | 연간·음력일 | 소원(+사주) |
| 다시 하면 | 같은 값 | **다른 값** → 하루 1회 제한 | 같은 값 | 같은 값 |
| 주기 | 매일 | 매일 | 날·해 | **바뀌지 않음** |

**공유 섹션의 위치** — 공유 카드는 `#result`의 **맨 마지막**에 두었습니다.
생년월일을 입력하지 않고 STEP 5에서 이탈하는 사용자도 공유할 수 있어야 하기 때문입니다.
STEP 6까지 진행하면 카드와 공유 문구에 띠·오행이 자동으로 추가됩니다.

**입력 문구** — 본명·닉네임·핸들네임 모두 가능하다는 것을 히어로, 입력 위 안내박스,
입력 힌트 세 곳에 명시했습니다. 개인정보에 민감한 사용자가 이탈하지 않도록 하는 것이
이 서비스의 전환율에 직접 영향을 줍니다.

## 설계 판단

### 후리가나는 사용자가 직접 입력받는다

`田中 愛`를 「あい」로 읽는지 「めぐみ」로 읽는지는 **기계가 확정할 수 없습니다.**
일본 이름의 한자 읽기는 다의적이라 자동 추정이 원리적으로 불가능합니다.

그래서 일본 웹폼의 표준 방식대로 **姓/名 각각의 한자(임의) + 후리가나(필수)** 를 받습니다.
문화적으로도 자연스럽고, 오독 리스크가 사라집니다.

- 한자는 **임의** → 닉네임·가타카나 이름만으로도 진단 가능 (STEP 3은 자동 숨김)
- 후리가나는 **필수** → 한글 변환의 근거

### 가나 → 한글은 "발음 그대로(유기음)" 방식

`たなか` → **타나카** (`다나카` 아님).

한국 어문 규범의 외래어 표기법이라면 어두 무성음을 평음으로 적어 `다나카`가 됩니다.
하지만 이 서비스는 **학습자가 소리를 익히는 것**이 목적이므로,
실제 발음에 가까운 유기음 표기를 택했습니다.

> 규범 표기(`다나카`)로 바꾸려면 `KANA1` 테이블의 か/た행을 평음으로 교체하면 됩니다.
> 두 표기를 동시에 보여주는 것도 검토할 만합니다.

### 구현된 가나 규칙

| 규칙 | 예 |
|---|---|
| 요음 (2글자) | `しゅん` → 슌 |
| 撥音 `ん` → 종성 ㄴ | `しんばし` → 신바시 |
| 促音 `っ` → 종성 ㅅ | `さっぽろ` → 삿포로 |
| 장음 `ー` 생략 | `ケンタロー` → 켄타로 |
| 장모음 `おう`/`うう` 축약 | `とうきょう` → 토쿄 |
| **단, 뒤에 모음이 오면 축약 안 함** | `いのうえ` → 이노우에 (`이노에` 아님) |

마지막 규칙이 핵심입니다. `のう`가 장음 「nō」인지 「no-u」인지 가나만으로는 구별되지 않으므로,
**`う` 다음에 모음이 오면 독립 모라로 판정**합니다.

### 받침(パッチム)에 따른 조사 변화

한글 유니코드 음절을 분해해 종성 유무를 판정하고, 조사를 자동 선택합니다.
문법적으로 정확할 뿐 아니라, **왜 그렇게 되는지 화면에 설명**해 학습 요소로 쓰입니다.

| | 받침 있음 | 받침 없음 |
|---|---|---|
| 제 이름은 ~ | 켄**이에요** | 아이**예요** |
| 주격 조사 | 켄**이** | 아이**가** |
| 호칭 (친근) | 켄**아** | 아이**야** |

### 장면 회화 — 이름을 넣은 상황극

STEP 4 안에 `<details>` 로 접어 두고 「簡単な会話を見てみよう →」를 누르면 열립니다.
바로 노출하지 않은 이유는, STEP 4의 본체가 **문형과 조사 학습**이고 회화는 응용이라
먼저 보이면 초점이 흐려지기 때문입니다.

장면은 7개(카페·교실·소개·공항·식당·메신저·회사)이며 **랜덤 선택**입니다.
「別の場面を見る」로 다시 뽑을 수 있고, **직전과 같은 장면은 나오지 않습니다.**
존댓말·반말, 씨·님·아/야가 골고루 들어가도록 배치했습니다.

**이름 치환 규칙** — `SCENES` 의 문자열에 플레이스홀더를 씁니다.

| | 결과 |
|---|---|
| `{name}` | 한국어 줄은 한글 이름, **일본어 줄은 후리가나** |
| `{ieyo}` | 이에요 / 예요 |
| `{eun}` `{ga}` | 은/는, 이/가 |
| `{voc}` | 이름 + 아/야 |

> **주의** — 조사는 **직전 글자**를 따릅니다. `{name} 씨는` 처럼 사이에 다른 말이 끼면
> 그 말(`씨`)에 맞춰 직접 써야 합니다. `씨{eun}` 으로 쓰면 이름의 받침을 보게 되어
> `켄 씨은` 같은 오류가 납니다(실제로 한 번 냈고 고쳤습니다).

### 한국식 성명학 = 자음 오행

### 왜 `window.open()` 을 쓰면 안 되는가 (실제 발생한 버그)

「공유 버튼을 누르면 앱이 아니라 웹 로그인 화면이 뜬다」는 문제가 있었습니다.
원인은 두 가지였습니다.

**1. `window.open()` 은 OS 의 앱 라우팅을 우회한다**

iOS Universal Links / Android App Links 는 **사용자가 링크를 탭했을 때** OS 가
설치된 앱으로 넘기는 구조입니다. JS 에서 `window.open()` 으로 열면 이 판정을
거치지 않고 브라우저가 열립니다. **브라우저 세션은 앱 로그인 상태를 공유하지
않으므로**, 앱에 로그인해 둔 사용자에게도 로그인 화면이 나옵니다.

→ X·Threads·LINE 버튼을 `<button>` + `window.open()` 에서
**실제 `<a href>` 로 교체**했습니다. `href` 는 결과 표시 시점에 채웁니다.

**2. LINE URL 이 애초에 웹용이었다**

`social-plugins.line.me/lineit/share` 는 **웹 소셜 플러그인**이라 웹 페이지가
열립니다. 앱을 여는 것은 `line.me/R/share` 입니다
([LINE URL scheme](https://developers.line.biz/en/docs/messaging-api/using-line-url-scheme/)).
LINE 은 `url` 파라미터가 없으므로 URL 을 `text` 안에 넣습니다.

**남는 한계** — Universal Link 는 사용자가 앱 측에서 꺼 두었거나, 브라우저 내
웹뷰(인앱 브라우저)에서 열린 경우 동작하지 않을 수 있습니다. 확실하게 앱으로
넘기는 유일한 경로는 `navigator.share` 이므로, **지원 기기에서는 이쪽을
주 버튼으로 크게 노출**하도록 바꿨습니다.

**Instagram에는 외부에서 투고 내용을 넘기는 공개 수단이 없습니다.** 이는 우회할 수 없는
플랫폼 제약이므로, 링크가 동작하는 척하지 않고 실제로 되는 흐름(이미지 저장 + 캡션 복사 →
앱에서 붙여넣기)을 구현하고 그 이유를 화면에 적었습니다. 모바일에서는 네이티브 공유
시트를 쓰면 Instagram을 직접 선택할 수 있으므로, 지원되는 기기에서만 해당 버튼을 노출합니다.

공유 카드는 **테마에 의존하지 않는 고정 색상**으로 그립니다. 다크 모드 사용자가 만든
이미지가 라이트 모드 사용자에게 다르게 보이면 안 되기 때문입니다.

공유 URL은 `location.origin + pathname`을 사용하고, `file://`로 열었을 때만
`SITE_URL` 상수로 대체합니다. 따라서 어디에 배포해도 올바른 링크가 붙습니다.

### 개인정보와 광고

**입력값(이름·생년월일)은 저장·전송되지 않습니다.** 진단은 전부 브라우저 안에서 끝나고,
앱 자체는 입력값을 어디로도 보내지 않으며 `localStorage`도 쓰지 않습니다.

단, **Google AdSense와 Google 애널리틱스를 넣은 시점부터 "외부 요청 0개"는
더 이상 사실이 아닙니다.** `<head>`에서 `pagead2.googlesyndication.com` 과
`googletagmanager.com` 스크립트를 불러오고, 광고 게재와 접속 분석을 위해 Cookie가
설정될 수 있습니다. 이름·생년월일이 어느 쪽으로도 넘어가지는 않지만,
"아무것도 외부로 나가지 않는다"는 문구는 거짓이 되므로 화면 문구를 아래처럼 분리했습니다.

- 이름·생년월일 → 저장·전송 안 함 (여전히 사실, 그대로 유지)
- 광고·분석 Cookie → 사용함을 명시 + 각각의 옵트아웃 경로 안내

**GA4(`G-93VGD4GH58`)를 추가할 때 `privacy.html` 4항이 「アクセス解析ツールを
使用していません」로 되어 있어 함께 고쳤습니다.** 도구를 붙이면서 폴리시를 그대로 두면
폴리시가 곧바로 거짓이 됩니다 — 추적 도구를 추가할 때는 항상 4항을 같이 볼 것.

일본 사용자는 개인정보에 민감하므로, 애매하게 뭉개는 것보다 두 가지를 분리해
명확히 적는 편이 신뢰에 유리합니다.

### 동의 관리(CMP) — 코드가 아니라 대시보드에서 하는 일

EU·영국(GDPR)과 캘리포니아(CCPA/CPRA) 트래픽에는 동의 확인이 필요합니다.
**Google은 EEA·영국 트래픽에 대해 "Google 인증 CMP" 사용을 요구합니다.**

중요한 점은, 이것이 **코드로 넣는 것이 아니라는 것**입니다. AdSense 관리화면의
**プライバシーとメッセージ**에서 GDPR 메시지와 CCPA 메시지를 만들어 게시하면,
이미 페이지에 있는 AdSense 스크립트가 CMP를 자동으로 주입합니다.

```
AdSense → プライバシーとメッセージ → GDPR   → メッセージを作成 → 公開
                                  → CCPA   → メッセージを作成 → 公開
```

**직접 만든 쿠키 배너는 의도적으로 넣지 않았습니다.** 자체 제작 배너는 IAB TCF 인증을
받을 수 없어 GDPR 요건을 충족하지 못하면서, 겉보기에만 준수한 것처럼 보이게 만듭니다.
없는 것보다 나쁩니다. 코드 쪽에서 할 수 있는 정당한 조치는 프라이버시 폴리시에
GDPR·CCPA 항목을 정확히 기재하는 것까지이고, 그건 `privacy.html` 6·7항에 넣었습니다.

#### Cloudflare → Apache 로 옮길 때의 진짜 위험

**이 사이트는 SPA 가 아닙니다.** 독립 HTML 4장이므로 "전부 index.html 로 보내는"
SPA 폴백을 넣으면 안 됩니다. 넣으면 없는 URL 까지 200 을 반환해 404 가 죽습니다.

필요한 것은 그 반대입니다. 사이트 내부 링크 18곳이 `/privacy` 같은 **확장자 없는 URL**
인데, Cloudflare Pages 는 이것을 자동으로 해결해 주지만 **Apache 는 아무것도 하지
않습니다.** 그대로 옮기면 사이트 내 링크가 전부 404 가 됩니다.

→ `.htaccess` 에서 내부 재작성으로 해결합니다:

```apache
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteCond %{REQUEST_FILENAME}.html -f
RewriteRule ^(.+?)/?$ $1.html [L]
```

실제 Apache 2.4 를 띄워 검증했습니다:

| 경로 | 결과 |
|---|---|
| `/` `/privacy` `/contact` `/tips` | 200 |
| `/kanji.json` `/ogp.png` `/ads.txt` | 200 |
| `/no-such-page` | **404** (SPA 폴백이 아님을 확인) |
| `/privacy.html` | 301 → `/privacy` (중복 URL 정규화) |
| `/data/kanji_platform.db` `/README.md` | 403 |

#### www の向きはサーバーに合わせる

このサーバーは apex → www の 301 をすでに返している（サーバーパネルの統一設定）。
`.htaccess` に逆向き（www を外す）を書くと

```
apex →(サーバー)→ www →(.htaccess)→ apex → …
```

で**無限ループになりサイトが落ちる**。そのため `.htaccess` は www 側に寄せている。
apex を正にしたい場合は、先にパネルの統一設定を解除してから
`.htaccess` の向きを変え、`set-site-url.py` で canonical も入れ替えること。

実 Apache で確認済み — apex は www へ 301 が1回、www は 200 で停止（リダイレクト0回）。

> **주의 — 실제로 한 번 사고를 냈습니다.** 초판은 "제외 목록에 없는 호스트를 전부
> 치환"하는 방식이었는데, 제외 목록에 `googlesyndication.com` 만 넣고 실제 호스트인
> `pagead2.googlesyndication.com` 을 놓쳐서 **AdSense 와 GA 의 script src 까지
> 바꿔버렸습니다.** 지금은 `index.html` 의 canonical 에서 자기 호스트를 특정하고
> **그 호스트만** 치환합니다. 워크플로의 Verify 단계에서도 매번 확인합니다.

```js
//    ^한국음   ^일본어뜻   ^한국어단어  ^그 뜻   ^예문 [한국어, 일본어]
```

한자음만 필요하면 `.db` 에 넣고 재생성하면 됩니다.
어느 쪽에도 없는 한자는 `?` 로 표시되고 STEP 3에서 제외됩니다.

### 남은 공백: 人名用漢字

DB는 **상용한자만** 수록합니다. 일본 인명에는 人名用漢字(863자)도 쓰이는데,
측정해 보니:

- **성씨**: 빈출 80자 중 미수록 0자 — 성씨는 상용한자로 거의 해결됩니다
- **이름**: 빈출 36자 중 **8자 미수록** (`凛 莉 葵 蓮 隼 颯 駿` 등)

즉 `宮崎 駿` 은 `궁기 ?` 가 됩니다. 현대 일본 이름에 인기 있는 글자들이라
`.db` 에 人名用漢字를 추가하는 것이 다음 우선순위입니다.

### 1. 배포 관문 — 저장소에 있고, push 할 때마다 돌아갑니다

여기서 잡은 것 중 화면으로는 절대 못 봤을 것들:

- **균시차의 부호가 반대**였습니다. 크기는 맞고 부호만 틀려서, 시지(時支)가 경계에서
  통째로 한 칸 밀립니다. 공표값과 맞추지 않았으면 발견할 수 없었습니다
- **「1984-02-02 = 갑자일」은 사실이 아닙니다.** 그날은 병인(丙寅)이고 갑자일은 1984-01-31.
  1984년이 갑자「년」인 것과 뒤섞인 설로 보입니다
- 항목별 점수 평균이 어긋나 **건강운만 매일 낮게** 나왔습니다. 십이지 12개 중 토가 4개라
  사주에 토가 많은 게 정상인데 기대치를 1/5로 잡은 탓
- **`index.html`의 `<label>` 7개에 `for`가 없었습니다.** 화면에는 라벨이 보이지만
  읽어주기에는 아무것도 전달되지 않고, 라벨을 눌러도 입력칸으로 이동하지 않습니다.
  나중에 만든 `gilbang`·`amulet`에는 붙어 있어서, 첫 페이지만 뒤처져 있었습니다

### 2. 개발 중 1회성 검증 — 저장소에 없습니다

아래는 개발 당시에 손으로 돌린 것으로, **자동으로 다시 돌지 않습니다.**
회귀를 막아 주지 않으므로 관문과 구분해 둡니다.

jsdom 기반 **53케이스** (변환 20 · 조사 5 · 날짜 7 · 검증 2 · 문구 5 ·
표시 제어 2 · 공유 10). 한국어 정확성 관련:

- 월 이름 불규칙: **6월 = 유월**, **10월 = 시월** (육월/십월 아님) — 화면에 설명 포함
- 연도는 한자어 수사로: `1995년` → **천구백구십오년**
- 윤년 검증: 1900-02-29 거부
- 받침에 따른 조사: `켄이에요`/`아이예요`, `켄이`/`아이가`, `켄아`/`아이야`

공유 카드는 `node-canvas`로 실제 PNG를 렌더링해 눈으로 검증했습니다.
이 과정에서 잡은 버그:

1. 「韓国語では」 라벨과 큰 한글 이름이 **겹침** — `textBaseline='alphabetic'`으로
   어센더를 계산하지 않고 커서를 옮긴 탓. 블록 높이를 먼저 합산해 세로 중앙 배치하는
   방식으로 재작성
2. 8음절 초과 이름의 자모 박스가 **조용히 잘림** — 마지막 칸을 `…`로 그려 명시
3. 한자음·띠가 없는 닉네임 카드의 **하단이 텅 빔** — 중앙 배치로 해결

렌더링 검증 케이스: 풀네임+STEP6 / 닉네임만 / 7음절 / 9음절(초과) / STEP5까지만.
