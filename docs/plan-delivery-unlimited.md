# plan-delivery-unlimited.md — 일수 제한 일시 해제 (7일 이후에도 계속 배신)

작성: 2026-08-16 · 상태: **구현 완료 · 배포 대기**
지시: 대표 「7일 이후에는 배신이 안 되게 되어 있는데 일단 이거 풀어놔. 나중에 추가하는 걸로 하고 계속 배신될 수 있게 해」

---

## 1. 왜 지금 푸는가

체험 7일을 다 쓰면 다음 날 아침부터 배신이 멈춘다(잔여 = `days_entitled - days_used` ≤ 0).
그런데 **결제는 열 수 없다** — Stripe 심사 대기(`SALES_MODE=test`)이고, 사업 전환
([plan-fortune-removal](plan-fortune-removal.md)) 이 끝나야 재신청할 수 있다.

즉 지금 멈춘 사람에게는 **살 방법이 없다.** 강좌가 조용히 끝나고, 그 사람은 돌아오지 않는다.
전환 기간 동안은 계속 배신한다.

---

## 2. 배신을 멈추던 곳은 한 곳뿐이었다

조사 결과 잔여 일수를 보는 관문은 **`push-daily.mjs` 의 분기 하나**다.

| 볼 만한 곳 | 실제 |
|---|---|
| `DELIVERABLE_SQL`（배신 대상 SQL） | 잔여로 **거르지 않는다**. `remaining` 을 계산해 실어 보낼 뿐 |
| `learning.advanceDay` | 잔여를 **보지 않는다**. `days_used + 1` 만 한다 |
| `users.status` | `trial`/`active` 그대로. 체험 만료로 상태를 바꾸는 코드는 **없다** |
| `subscriptions.trial_end` | 날짜는 갖지만 **결제 게이트(`inTrialNow`) 전용**. 배신을 안 막는다 |
| **`push-daily.mjs` `remaining <= 0`** | **여기서만 멈춘다** ← |

그래서 이 한 줄만 열면 된다. 다른 곳을 손댈 필요가 없었다.

---

## 3. 무엇을 바꿨나

### 3-1. 스위치 1개 — `server/lib/repo/billing.mjs`

```js
export const DELIVERY_UNLIMITED = true;
```

**환경변수가 아니라 코드 상수로 둔 이유.** 이 저장소의 방식은 「코드가 정본」이다
(웰컴보드·리치메뉴와 같은 원칙). env 로 두면 cPanel 화면에만 있는 사실이 하나 늘고,
관문이 볼 수 없게 된다. 상수면 되돌리는 것도 `true` → `false` 한 글자다.

### 3-2. 읽는 곳은 2군데뿐

```diff
@@ server/db/push-daily.mjs — 잔여 0 의 아침 @@
-  if (remaining <= 0) {
+  if (remaining <= 0 && !DELIVERY_UNLIMITED) {
```

```diff
@@ server/db/push-evening.mjs — 6일차 저녁의 체험 종료 예고 @@
 async function trialUpsellSection(conn, u) {
+  if (DELIVERY_UNLIMITED) return null;
```

**저녁 쪽을 빼먹으면 안 된다.** 6일차 저녁에 「明日が最後の 1 日です」라고 말한
**다음 날 아침에 8일차가 도착**한다. 말한 것과 일어나는 일이 어긋나고, 받은 쪽에서는
어느 쪽이 맞는지 확인할 방법이 없다. 여기가 이 작업에서 유일하게 놓치기 쉬운 곳이었다.

### 3-3. 판정은 지우지 않고 **남겼다**

`remaining <= 0` 분기 자체는 그대로 있다. 지우면 제한을 되돌리는 날
「어디서 멈추고 있었는지」를 다시 찾아야 한다.

---

## 4. 일수 소비는 **계속한다** (개발 판단 — 이견 있으시면 되돌립니다)

`advanceDay` 는 손대지 않았다. 해제 중에도 `days_used` 는 계속 늘고,
잔여는 **마이너스로 내려간다**.

**왜 멈추지 않았나.** 소비를 멈추는 버전을 만들면 「진행」 함수가 2개가 된다.
`learning.mjs` 가 명시적으로 「그래서 진행하는 함수는 하나만 둔다(`advanceDay`)」이고,
일자 확보와 일수 소비를 **한 문장**에서 하는 것이 STATUS §8-2 의 불변식이다.
어느 쪽을 부를지 헷갈리는 날 하루가 공짜가 된다.

**결과.** 무료로 배신한 만큼이 장부에 마이너스로 남는다. 이건 정확한 기록이다.

**되돌리는 날 무슨 일이 일어나는가 — 여기가 중요합니다.**
`false` 로 바꾸는 순간, 그때 잔여가 크게 마이너스인 사람들이 **그 아침부터 전원 정지**한다.
그것이 「제한을 되돌린다」는 뜻이다. 되돌리기 전에 **살 수 있는 상태**(`SALES_MODE=open`)인지
먼저 확인해야 한다 — 아니면 지금과 똑같은 막다른 길이 반복된다.

> 대안이었던 「해제 중에는 일수를 소비하지 않는다」를 택하면, 되돌린 날 모두에게
> 체험 7일이 그대로 남아 다시 7일이 무료로 나간다. 그쪽을 원하시면 말씀해 주십시오.

## 5. 부작용 점검 (전부 확인함)

| 것 | 해제 중 동작 | 판단 |
|---|---|---|
| 재구매 권유(`upsellNotice`) | 분기 안이라 **안 나감** | 맞다. 살 수 없는데 권유하면 안 된다 |
| 이탈 장부(`lapse_log`) | **안 열림** | 맞다. 이탈이 아니다 |
| 기한 예고(`expiringNotice`) | `hasPurchases` 가 조건이라 **원래 안 나감**（구매자 0） | 손댈 필요 없음 |
| 체험 종료 예고(저녁) | **막았음**（§3-2） | 안 막으면 거짓말이 된다 |
| 수료 안내(101일) | 그대로 나감 | 맞다. 원고가 101일에서 끝난다 |
| `maintain` drift 경고 | `days_entitled` 를 안 건드리므로 **변화 없음** | 오탐 없음 |
| 원고 없는 날 | 원래대로 일수 소비 없이 멈춤 | 변화 없음 |

**배신 상한.** 101일(`TOTAL_DAYS`)에서 자연히 끝난다. 무한히 나가지 않는다.

## 6. 관문 — 상수를 따라가게 만들었다

「해제 중의 동작」만 쓰고 원래 검사를 지우면, 되돌리는 날 **돈에 직결되는 약속**
(잔여 0 의 아침에 본편 0통·안내 1회·일수 불변)을 아무도 안 보게 된다.
그래서 관문이 `DELIVERY_UNLIMITED` 를 읽어 **양쪽 길을 다 들고 있게** 했다.

```js
if (DELIVERY_UNLIMITED) {
  assert(/^送信:/.test(r), `해제 중인데 멈췄습니다: ${r}`);
  ...
} else {
  assert(r === "日数切れ", r);   // 되돌리는 날 이쪽이 다시 효력
}
```

| 관문 | 항목 |
|---|---|
| `verify-push` | 「보유일수를 넘긴 아침의 처리」를 양쪽 분기로 · **신설** 「해제 중은 잔여 −33 이어도 배신」 · 「장부가 열려 있어도 안내 0」 |
| `verify-evening` | 「예고의 유무는 `DELIVERY_UNLIMITED` 를 따른다」 — 해제 중엔 **`trial_end` 기록도 남기지 않는다**(남기면 되돌린 날 「1회 한정」이 이미 소진된 상태가 된다) |
| `verify-evening` | 「문면이 판매 개폐로 안 갈린다」를 **`trialUpsellNotice` 직접 호출**로 변경 — 배신 경로를 거치면 해제 중엔 문면을 꺼낼 수 없다. 보고 싶은 건 문면이지 경로가 아니었다 |

**관문 18종 전부 PASS**（`verify-push` 53 · `verify-evening` 32）.

## 7. 되돌리는 법 (한 글자)

```js
// server/lib/repo/billing.mjs
export const DELIVERY_UNLIMITED = false;
```

되돌리기 전 확인:

1. `SALES_MODE=open` 인가 (아니면 또 막다른 길)
2. 그 시점 잔여가 마이너스인 사람 수 — `node db/with-env.mjs db/who.mjs` 의 `left=`
3. 되돌린 첫 아침에 전원이 「日数切れ」로 바뀐다는 것을 알고 있는가
