# P4 계획서 — 101일 콘텐츠 & 배포 배치

작성: 2026-08-03 / 선행: [research.md](research.md) · [plan-fortune-content.md](plan-fortune-content.md) §11

> 이 문서는 **계획**입니다. 승인 전까지 콘텐츠도 코드도 쓰지 않습니다.

---

## 1. 조사 결과 — P4 는 「원고 작성」만이 아닙니다

`content_templates` 가 0건이라 「101일분 글쓰기」로 보이지만, 조사해 보니
**보낼 수단 자체가 없습니다.**

| 있는 것 | 없는 것 |
|---|---|
| `content_templates` 스키마 | 행 **0건** |
| `learning.upsertTemplate()` 입고 API | 입고 스크립트 |
| `learning.getTemplate()` 조회 API | **{NAME} 치환 코드** |
| `line.pushMessage()` 발신 함수 | **배포 배치 진입점** |
| `push_logs` 중복 방지 스키마·색인 | 배치를 부르는 것 (cron) |

`{NAME}` 을 치환하는 코드는 **`db/smoke.mjs` 안의 시험용 문자열이 유일**합니다.
`app.mjs` 의 경로는 4개(`/webhook` `/link/start` `/link/callback` `/health`)뿐이고,
`package.json` 의 스크립트는 `start/migrate/migrate:check/smoke/verify` 로
**배치가 없습니다.**

→ **P4 는 세 덩어리입니다.** 순서를 지키지 않으면 원고를 다시 쓰게 됩니다.

```
P4-a  렌더러      템플릿 + 사용자 → 실제 보낼 메시지        ← 형식이 여기서 확정
P4-b  배포 배치   대상 추출 → 렌더 → 발신 → push_logs
P4-c  원고 101일  a 가 확정한 형식으로 작성
```

**c 를 먼저 하면 안 됩니다.** 렌더러가 확정되기 전 형식으로 101일을 쓰면,
치환 규칙이나 메시지 분할이 바뀔 때 101건을 전부 손봐야 합니다.

## 2. 확정된 형식 (스키마가 이미 정한 것)

```sql
content_templates (
  day_number         INT PRIMARY KEY,   -- 1〜101
  semester           INT NOT NULL,      -- 1〜4  ※ day_number 에서 자동 계산
  grammar_point      VARCHAR(100),      -- "-입니다 / -입니까?"
  grammar_tip_kr     TEXT,              -- 한·일 병기 짧은 설명
  dialogue_template  JSON,              -- [{kr, ja}] 3〜4문
  vocab_3            JSON,              -- [{kr, meaning, note}] ×3
  requires_name_slot BOOLEAN
)
```

학기 구분은 `learning.mjs` 의 `SEMESTERS` 가 **단일 출처**입니다.

| 학기 | 일자 | 일수 |
|---|---|---|
| 1 | 1–30 | 30 |
| 2 | 31–50 | 20 |
| 3 | 51–75 | 25 |
| 4 | 76–101 | 26 |

퀴즈는 **30·50·75일**(`quiz_checkpoints`). 101일은 수료 메시지라 퀴즈 없음.
`upsertTemplate()` 이 `semesterForDay(d)` 로 학기를 스스로 넣으므로,
**원고에 학기를 적지 않습니다** (적으면 두 곳에 진실이 생김).

## 3. P4-a 렌더러 — 먼저 정해야 할 것

### 3.1 치환 슬롯

`smoke.mjs` 에 두 가지가 등장합니다.

```js
dialogueTemplate: [{ kr: "{NAME}입니다.", ja: "{NAME_JP}です。" }]
```

| 슬롯 | 값 | 출처 |
|---|---|---|
| `{NAME}` | 한글 이름 (다나카) | `users.name_kr` |
| `{NAME_JP}` | 일본어 이름 (たなか) | `users.name_reading` |

**결정 필요 ①** — 조사(助詞)를 어떻게 처리할지.

한국어는 받침에 따라 조사가 바뀝니다. `{NAME}입니다` 는 항상 안전하지만,
`{NAME}는/은`, `{NAME}가/이`, `{NAME}야/아` 는 이름마다 달라집니다.

사이트 본체에는 **이미 받침 판정과 조사 선택이 구현되어 있습니다**
(`index.html` 의 `hasJong`/`ieyo`/`ega`, 장면 회화의 `fillName`).
서버에도 같은 규칙이 필요합니다.

- (가) 슬롯을 늘린다 — `{NAME_EUN}` `{NAME_GA}` `{NAME_VOC}` … 렌더러가 받침으로 고름
- (나) 조사 붙는 문장을 쓰지 않는다 — 원고 제약이 커짐

**(가) 를 권합니다.** 사이트에서 이미 검증된 규칙이고, 안 하면 「켄 씨은」 같은
문법 오류를 **학습 콘텐츠로 가르치게 됩니다.** 실제로 사이트에서 한 번 낸 오류입니다.

> 주의 — 조사는 **직전 글자**를 따릅니다. `{NAME} 씨는` 처럼 사이에 말이 끼면
> 그 말(`씨`)에 맞춰야 하므로, 슬롯을 이름 바로 뒤에만 쓰도록 원고 규칙에 못박습니다.

### 3.2 메시지 구성

**결정 필요 ②** — LINE 메시지 몇 통으로 보낼지.

하루치에 문법·회화·단어 3개가 들어갑니다. 한 통에 다 넣으면 길고,
나누면 알림이 여러 번 울립니다. LINE 은 1회 push 에 최대 5통까지 묶을 수 있습니다.

제안: **2통** — ①인사+문법+회화 ②단어 3개.
`pushMessage(to, messages[])` 가 이미 배열을 받으므로 한 번의 호출로 끝납니다.

### 3.3 이름이 없는 사용자

`requires_name_slot = true` 인 날에 `name_kr` 이 비어 있으면 어떻게 할지.

**결정 필요 ③** — (가) 그 날만 이름 없는 대체 문장 (나) 이름 입력 유도 후 보류

`users.name_kanji/name_reading/name_kr` 은 전부 NULL 허용이고,
LINE 만 등록하고 사이트 진단을 안 한 사람이 있을 수 있습니다.

## 4. P4-b 배포 배치

### 4.1 없는 것을 만듭니다

```
db/push-daily.mjs        (신규) 진입점. cron 이 부름
package.json scripts     "push": "node db/push-daily.mjs"
```

`app.mjs` 에 경로로 넣지 않습니다 — HTTP 로 노출하면 외부에서 배포를 유발할 수
있고, 인증을 또 만들어야 합니다. **cron 이 직접 부르는 스크립트**가 단순합니다.

### 4.2 배치가 지켜야 할 것

`push_logs` 스키마 주석에 이미 요구가 적혀 있습니다.

- **하루 2회 실행** — `ix_push_user_type_time` 색인이 그 전제로 설계됨
- **중복 발신 금지** — 같은 날 같은 `push_type` 이 있으면 건너뜀
- **실패도 기록** — `status='failed'`. 안 남기면 「배포가 멈춘 것」을
  이용자 문의로 알게 됨
- **이중 기동 방지** — `verify-server.mjs` 가 이미 검사 중(73항목에 포함)

### 4.3 JST 고정

`lib/jst.mjs` 가 있고 README 에 **「시각은 전부 JST. 서버 시계에 기대지 않습니다」**
라고 적혀 있습니다. 배치도 이를 따릅니다. ChemiCloud 서버 시계가 UTC 여도
「일본의 오늘」로 판정해야 합니다.

## 5. P4-c 원고 101일

### 5.1 분량

```
101일 × (문법 1 + 회화 3〜4문 + 단어 3)
= 문법 101개 · 회화 약 350문 · 단어 303개
```

**한 번에 쓰지 않습니다.** 1학기(30일)를 먼저 쓰고 렌더러·배치로 실제 발신까지
확인한 뒤 나머지를 채웁니다. 형식 문제는 30일치에서 드러납니다.

### 5.2 문법 배열 — 결정 필요 ④

101일을 무엇으로 채울지가 정해져 있지 않습니다. 후보:

- **(가) TOPIK I 문법 순서** — 검증된 순서, 교재와 대조 가능
- **(나) 사이트와 이어지는 순서** — 이름·자기소개에서 출발
  (`저는 {NAME}입니다` → 조사 → 시제 …)

**(나) 를 권합니다.** 사이트가 이미 「이름으로 배우는 한국어」이고,
1일차가 `{NAME}입니다` 로 시작하면 웹에서 LINE 으로 넘어온 사람에게
**같은 이야기의 연속**이 됩니다. (가)는 어느 교재로도 대체 가능한 콘텐츠가 됩니다.

### 5.3 입고 방법

원고를 **JSON 파일로 저장소에 두고**, 스크립트가 `upsertTemplate()` 로 넣습니다.

```
server/content/day-001.json … day-101.json   또는  content/semester-1.json
server/db/seed-content.mjs                   (신규) 입고 스크립트
```

- SQL `INSERT` 를 손으로 쓰지 않습니다 — 원고는 사람이 고치는 것이라
  JSON 이 읽고 쓰기 쉽습니다
- `upsertTemplate` 이 `ON DUPLICATE KEY UPDATE` 이므로 **몇 번 돌려도 같은 결과**
- `findMissingTemplateDays()` 로 빠진 날을 셀 수 있습니다 (이미 구현됨)

**결정 필요 ⑤** — 원고 JSON 을 공개 저장소에 둘지.
콘텐츠는 이 서비스의 자산입니다. 유료 배포물이 저장소에 그대로 있으면 누구나 받습니다.

## 6. 검증 계획

기존 방식(단정문 + 실제 대조)을 따릅니다.

| 대상 | 방법 |
|---|---|
| 슬롯 치환 | 받침 있는 이름/없는 이름 × 전 슬롯. 「켄 씨은」류가 안 나오는지 |

## 7-2. P4-a 결과 (2026-08-03) — 원고 형식 확정

`server/lib/render.mjs` + `tools/verify-render.mjs` (24항목 전건 통과).

### 원고 작성 규칙 — 여기서 확정된 것

| 슬롯 | 나오는 것 (켄 / 사쿠라) |
|---|---|
| `{NAME}` | 켄 / 사쿠라 |
| `{NAME_JP}` | けん / さくら ※일본어 줄 전용 |
| `{NAME_IEYO}` | 켄이에요 / 사쿠라예요 |
| `{NAME_EUN}` `{NAME_GA}` `{NAME_EUL}` `{NAME_WA}` `{NAME_VOC}` | 켄은 / 사쿠라는 … |

**조사 슬롯은 이름까지 포함해 치환됩니다.** 따라서

```
{NAME_EUN} 일본 사람입니까?      ← 맞음   켄은 …
{NAME}{NAME_EUN} 일본 사람입니까? ← 틀림   켄켄은 …  이름 중복
{NAME} 씨{NAME_EUN} …             ← 틀림   중복 + 조사가 씨를 따라야 함
{NAME} 씨는 …                     ← 맞음   씨는 모음 끝이라 는 고정
```

`findMisplacedSlot()` 이 위 2·3행을 잡습니다. 원고 입고 시 이걸 통과시킵니다.

> 이 함정은 **예시 원고를 실제로 렌더해 눈으로 읽다가** 발견했습니다.
> 단정문만 보면 `아이아이는` 이 `아이는` 을 부분포함해 통과해 버립니다.

### 그 외 확정

- **2통** — ①문법+회화 ②단어 3개 (결정 ② 대로)
- **회화는 1왕복마다 빈 줄**, 화자 `who` 는 **선택** (`{NAME_JP}` 도 사용 가능).
  없으면 문답이 혼잣말로 읽혀서 추가. 안 쓰는 날은 그대로 동작.
- **`hasJong` 은 판정 불가 시 `null`** (빈 값·한글 아님). `false`(받침 없음)와 구분.
- **이름이 필요한데 없으면 `null` 반환** → 호출측이 `nameMissingNotice()` 로 전환.
  기본 이름을 넣지 않습니다 (전원이 같은 이름으로 불림).

### 검증에서 본 것

한글 완성형 **11,172자 전수**로 받침 규칙 대조, `index.html` **실소스에서 조사 규칙을
읽어와** 서버와 대조(따로 관리하면 웹/LINE 이 갈림), 학기 경계 8개 + 1〜101일 전수.

## 7-3. P4-b 결과 (2026-08-03) — 아침 배포 배치

`server/db/push-daily.mjs` + `tools/verify-push.mjs` (18항목). `npm run push` 로 실행.

```
node db/push-daily.mjs              오늘분 배포
node db/push-daily.mjs --dry-run    누구에게 몇 일차가 갈지만 출력
node db/push-daily.mjs --date=…     그 날짜로 동작 (JST)
node db/push-daily.mjs --limit=10   앞 10명만
```

### 순서가 전부입니다

```
1  원고가 있는지 본다      없으면 아직 날을 소비하지 않음
2  날을 확보한다            advanceDay. 못 얻으면 내려감
3  보낸다
4  기록한다
```

- **2 를 3 보다 먼저** — 보내고 진행하면, 발신은 성공했는데 진행이 실패한 날에
  다음 날 아침 같은 내용이 또 갑니다. 반대는 그날이 안 가지만 `push_logs` 에 남습니다.
- **1 을 2 보다 먼저** — `content_templates` 가 아직 0건이라, 원고 없는 날 확보만
  진행하면 **아무도 안 읽은 하루가 조용히 사라집니다.** 지금 실제로 일어나는 상황입니다.

### 결정 ③ 확정 — 이름 없는 사용자

**건너뛰지 않고, 그날은 이름 등록 안내로 대체합니다.** 건너뛰면 그 사람만
101일의 수가 어긋납니다. 기본 이름은 넣지 않습니다(전원이 같은 이름으로 불림).

### 그 외 확정

| 상황 | 처리 |
|---|---|
| 오늘 이미 보냄 | 확보도 안 함 |
| 보유일수 초과 | 안 보냄 (upsell 은 별도 편) |
| 101일 완료 | 진행 안 함 (completion 문면은 P4-c) |
| LINE 403/404 | 차단·탈퇴 → 대상에서 제외 |
| LINE 500 | 제외하지 **않음** (일시 장애로 명단이 비는 것 방지) |
| `PUSH_DISABLED=1` | 확보도 안 함 (비상정지가 날을 먹으면 안 됨) |
| 재시도 키 | `sha256(user:day:type:date)` → 매번 같은 UUID |

### 남은 것

- **저녁 복습(`review`)** — `listReviewTargets()` 는 이미 있으나 **문면이 미정**.
  P4-c 에서 정합니다. 지어내지 않았습니다.
- `quiz`(30/50/75) · `upsell` · `completion` 문면도 P4-c.

## 7-4. P4-c 1학기 (2026-08-03) — 30일 입고 완료

본번 DB 에 **30일 입고 완료**. `findMissingTemplateDays()` → 남은 71일(31〜101).

### 결정 ⑤ 확정 — 원고는 공개 저장소에 두지 않습니다

이 저장소는 public 입니다. 101일은 **유료로 파는 것**이고, 한 번 push 하면
지워도 히스토리에 남습니다 — `.env` 와 같은 성질입니다.

```
server/content/          .gitignore (원고 본체)
server/lib/content-check.mjs   커밋함 (받아들이는 조건)
server/db/seed-content.mjs     커밋함 (입고)
```

**받아들이는 조건은 코드이므로 남깁니다.** 원고를 갖고 있지 않은 사람도
무엇을 만족해야 하는지는 읽을 수 있습니다.

서버로는 cPanel 파일 API 로 직접 올립니다. `.cpanel.yml` 의 동기화가

### 배포 시각을 cron 이 아니라 코드가 정합니다

```
cron:  0 * * * *  bash ~/kstudy101-line/db/push-cron.sh
배치:  --not-before=7   ← 일본 시각으로 판단
```

공유 서버의 cron 은 **서버 지방시**로 돕니다. 그게 무엇인지는 빌린 쪽에서
확인하기 어렵고, 이전·서머타임으로 조용히 어긋납니다. **일본의 7시**에
보내고 싶은 것이지 이 기계의 7시가 아닙니다. 그래서 매시 호출하고
시각 판단은 코드가 합니다.

「7시 정각만」이 아니라 「7시 이후」인 이유 — 7시 회차가 실패한 날
8시가 줍습니다. 두 번 안 가는 건 `sentToday` 가 봅니다.

### cron 에서만 드러난 것

**`set -u` 가 CloudLinux 의 `activate` 와 충돌해 매 회차가 죽고 있었습니다.**
`activate` 가 정의되지 않은 `CL_VIRTUAL_ENV` 를 읽습니다.

배포 경로의 下見 에서는 **바깥 셸이 먼저 activate 를 마친 뒤**라 통과했습니다.
「시험한 길」과 「본번에서 지나는 길」이 달랐던 것이고, **cron 에서 실제로
쏘아 보고서야** 드러났습니다. 로그에 `unbound variable` 3줄만 남고
아무것도 안 갔습니다.

## 7-6. 결정 ③ 재검토 (2026-08-03) — 이름 없는 사람은 날을 소비하지 않습니다

**앞선 결정이 틀렸습니다.** 「건너뛰지 않고 안내로 대체하고 날은 진행」은
101일의 **수**는 지키지만 **내용**을 비웁니다.

1〜5일차가 전부 이름을 쓰므로, 사이트를 안 거치고 친구추가만 한 사람은
**체험 3일 동안 본문을 한 번도 못 보고** 끝났습니다. 게다가 그 날들은
소비되어 **나중에 이름을 넣어도 영영 안 왔습니다.**

| | 이전 | 지금 |
|---|---|---|
| 날 진행 | 진행함 | **멈춤** |
| 나중에 이름 등록 | 1〜5일차 손실 | **그 날부터 시작** |
| 안내 횟수 | 매일 | **2회, 이후 침묵** |

매일 보내면 차단당하고, **차단은 되돌릴 수 없습니다** — 나중에 고쳐도 안 닿습니다.
침묵 중에도 진행은 멈춘 채이므로, 30일 뒤에 이름을 넣어도 1일차부터 이어집니다.

안내는 `day_number` 와 함께 `push_logs` 에 남고, **그 행 수가 곧 안내 횟수**입니다
(열을 추가하지 않았습니다).

### 친구추가 인사 추가

`follow.mjs` 가 **아무것도 안 보내고 있었습니다.** 첫 접촉이 다음날 아침의
「お名前を登録してください」 한 줄이라, 무엇에 관한 것인지 알 수 없었습니다.
이름이 없는 사람에게만 강좌 설명 + 진단 링크를 보냅니다.
사이트를 거쳐 온 사람에게는 안 보냅니다(이미 이름이 있음).
