## 1. 고친 결함 ①  답한 질문이 그대로 다시 온다

**어디** — [server/lib/handlers/postback.mjs](../server/lib/handlers/postback.mjs) `stateOf` / `followUp`

`handlePostback`은 맨 앞에서 `users` 행을 한 번 읽고, 그 뒤에 버튼을 처리합니다.

```js
const user = await users.findByLineUserId(conn, lineUserId);   // ← 여기서 읽음
...
await users.setNameSource(conn, user.id, use);                 // ← DB 갱신
const replied = await reply(token, [await followUp(conn, user)], send);
//                                                    ↑ 갱신 전 행
```

`followUp` → `stateOf(conn, user)` 가 `{ ...user, ... }` 로 펼치므로
**방금 쓴 `name_source` 가 옛 값(`null`)으로 덮입니다.**
`nextStep` 은 「아직 이름을 안 물어봤다」로 읽고 ① 이름 확인을 다시 보냅니다.

`saju` 와 `progress` 는 `stateOf` 안에서 다시 읽고 있었습니다.
그래서 **생년월일과 코스는 진행되는데 이름만 진행되지 않는** 형태로 나왔습니다.
`link.mjs` 의 `completeLink` 는 같은 이유로 `findById` 를 한 번 더 끼워두었는데
(그쪽 주석에 이유가 적혀 있습니다), 이쪽만 빠져 있었습니다.

**실측**

```
DB 는 갱신됨          name_source = web
갱신된 행으로 판정하면 nextStep = birth
실제로 돌아온 것       "① お名前の確認"     ← 방금 답한 질문
```

**이용자에게 보이는 것** — 「武田 花子で」를 눌러도 같은 질문이 같은 버튼과 함께
다시 옵니다. 몇 번을 눌러도 ①에서 움직이지 않고, ② 생년월일과 ③ 코스에
영원히 도달하지 못합니다.

**고침** — `stateOf` 가 `userId` 만 받아 `users` 행도 함께 다시 읽습니다.
세 표를 전부 갱신 후의 값으로 읽으므로, 이 계열의 어긋남이 다시 생기지 않습니다.

## 2. 고친 결함 ②  생년월일을 건너뛴 사람에게 배치가 매일 죽는다

**어디** — [server/lib/onboarding.mjs](../server/lib/onboarding.mjs) `nextStep`
+ [server/db/push-daily.mjs](../server/db/push-daily.mjs) `deliverOne`

`nextStep` 은 「다음에 물을 것」을 **하나만** 돌려주고, 순서는
`name → birth → track` 입니다. 배치는 이렇게 읽고 있었습니다:

```js
const step = nextStep(u);
if (step === "name" || step === "track") return askOnboarding(...);
```

생년월일은 배신을 멈추지 않는 단계입니다(멈추는 건 운세뿐). 의도는 맞습니다.
그런데 **이름은 답했고 생년월일은 건너뛴 사람**은 `nextStep` 이 `"birth"` 를
돌려주므로, `track` 이 비어 있어도 이 분기를 통과해 버립니다. 그 다음 줄:

```js
const tpl = await learning.getTemplate(conn, u.track /* null */, next);
//  → learning.mjs: if (!isTrack(track)) throw new Error(`未知の track: ${track}`)
```

**실측**

```
nextStep = birth                     (배치는 name / track 만 붙잡는다)
✗ 배치가 예외로 떨어집니다 — "未知の track: null"
```

**떨어지는 방식이 나쁩니다.** 예외는 `main()` 의 try/catch 가 잡아
「処理中の異常」으로 세고, cron 은 매일 실패로 끝납니다. 본인에게는
아무것도 가지 않지만 이유는 어디에도 나오지 않습니다 —
받는 쪽에서는 「오늘은 안 오네」로만 보입니다.

생년월일 질문을 후회 없이 후회 없이 뒤로 미루는 것만으로 이 상태가 됩니다.
드문 경우가 아닙니다.

**고침** — 판정식을 한 곳(`PENDING`)에 모으고, 「배신을 멈추는 단계」만
보는 `blockingStep()` 을 따로 냈습니다. `nextStep` 과 술어를 공유하므로
단계가 늘어도 진실이 두 곳이 되지 않습니다.

```js
const PENDING = Object.freeze({
  name:  (u) => !u.name_source && !!u.name_kr && !!u.display_name,
  birth: (u) => !!u.birth_date && !u.birth_confirmed,
  track: (u) => !u.track
});
export function nextStep(u = {})     { return STEPS.find((s) => PENDING[s](u)) || null; }
export const BLOCKING_STEPS = Object.freeze(["name", "track"]);
export function blockingStep(u = {}) {
  return STEPS.find((s) => BLOCKING_STEPS.includes(s) && PENDING[s](u)) || null;
}
```

## 3. 요구사항별 실기 결과

### 3.1 웹 → LINE 인계 (요구 1)

```
✓ 웹 본문 8항목이 그대로 정규화된다      이름 3종 / 생년월일 / 시각 / 오행 / 진단결과
✓ UTC 밤을 날짜로 받아들이지 않는다       잘라내지 않고 통째로 거부
✓ 합언어(state)와 인증 URL을 돌려준다     state 43자 / DB엔 해시만 / 30분
```

`"1995-04-12T23:00:00Z"` 를 앞 10자로 자르면 통과해 버리는데(UTC 23시는
JST로 다음날 → 일주가 하루 밀림), 자르지 않고 통째로 거부하는 것을 확인했습니다.

### 3.2 어느 이름·어느 생년월일로 (요구 1의 핵심)

```
✓ 단계 순서는 이름 → 생년월일 → 코스              name → birth → track → null
✓ 고를 수 없는 사람에겐 묻지 않는다                비교할 상대가 없으면 건너뜀
✓ 「사이트 이름으로」→ 기록되고 다음 질문이 나온다   name_source=web → 곧바로 ② 생년월일
✓ 「LINE 이름으로」→ 웹 이름을 지우고 사이트로       name_kr 삭제 → 재진단 안내
✓ 「이 생년월일로」→ 확인 도장, 코스로 진행          birth_confirmed=1 → ③ 코스
✓ 「입력 다시」→ 확인 도장을 찍지 않는다             가짜 생년월일 그대로 진행 안 됨
✓ 확인 전에는 운세를 붙이지 않는다 (레슨은 보냄)     birth_confirmed=0 → 운세 없음
```

**「LINE 이름으로」를 고르면 사이트로 되돌립니다.** 한글 표기(다케다 하나코)를
만들려면 사이트의 `hanja_db`/`kanji.json` 이 필요한데 서버에 없기 때문입니다
(`.cpanel.yml` 이 옮기는 건 `saju.js`/`fortune.js`/`solar-terms.json` 3개뿐).
변환표를 2부로 만들면 웹과 LINE에서 같은 이름이 다른 한글이 됩니다.

**생년월일도 마찬가지로 사이트로 되돌립니다.** LINE에서 직접 받으면
`1995/4/12`·`H7.4.12`·`1995-04-12` 를 LINE 쪽에서도 해석해야 하고,
해석이 갈리면 사주가 달라집니다.

### 3.3 서비스 안내 (요구 2)

연동 직후 `serviceGuide()` 1통이 갑니다. 5개 요점이 다 들어 있는 것을 확인:

```
✓ 이름으로 배움      韓国語を、{이름}さんの**名前**と**四柱**で学びます
✓ 내가 주체인 회화   教科書の「ミンスさん」ではなく、例文の主語があなたです
✓ 한국식 운세        韓国式の占い（사주・운세・기운）が毎朝つきます
✓ 하루 2회           朝 7時 … / 夕 6時 …（복습·퀴즈는 일수 안 깎음을 명시）
✓ 3코스              初級 / 中級 / 上級 の3つ。それぞれ101日ぶんの別の講座
```

친구추가만 하고 사이트를 안 거친 사람에겐 `welcomeForNameless()` 가
따로 가고, 이름 등록을 위해 사이트로 안내합니다.

### 3.4 코스 선택 (요구 3)

```
✓ 고르면 기록되고, 두 번째 누름은 덮어쓰지 않는다   beginner 확정 / advanced 거부
✓ 모르는 코스 이름은 DB 에 닿기 전에 막힌다        ENUM 밖은 거부
✓ 3단계를 다 답하면 더 묻지 않는다                온보딩 완료
```

`setTrack` 이 `WHERE track IS NULL` 이라, 연타나 옛 화면을 거슬러 올라가
다시 눌러도 진행 중인 코스가 바뀌지 않습니다. 세 코스는 각각 **독립한 101일**입니다.

### 3.5 아침 7시 (요구 4)

```
✓ 일본 시각 7시 전에는 아무것도 하지 않는다   6시 대기 / 7시 이후
✓ 사주에서 실제로 운세가 나온다               총운 37점 소길(小吉) / 십신 편인
✓ 웹과 같은 인수로 부른다 (출생지 고정 아님)
✓ 아침 배신은 3통                             문법+회화 / 단어3 / 운세
✓ 회화문의 주어가 본인 이름, 조사가 받침에 맞음
✓ 운세에 그날 문법으로 다시 말한 한 줄이 붙는다  fortune_bridge 반영
✓ 원고가 없는 날은 일자를 소비하지 않는다
```

실제로 도착하는 것(1통째·3통째 발췌):

```
📚 4日目
【今日の文法】-예요 / -이에요
打ち解けた丁寧。パッチムがあれば 이에요、なければ 예요。

たけだ はなこ：안녕하세요. 저는 다케다 하나코예요.
こんにちは。私はたけだ はなこです。

점원：다케다 하나코는 어디에서 왔어요?
たけだ はなこさんはどこから来ましたか？
```
```
🔮 오늘의 운세　총운 소길（小吉）
…
오늘은 정인의 날이라 배움에 좋습니다.
…
──────────
오늘의 총운은 「좋아요」예요. 배운 -예요 로 말해 보세요.     ← 그날 문법 적용
```

「다케다 하나코**예요**」/「다케다 하나코**는**」 — 받침 없는 이름이므로
`-이에요`·`-은` 이 아니라 `-예요`·`-는` 가 붙었습니다. 규칙은 사이트
`index.html` 의 것을 그대로 옮겼고, `verify-render.mjs` 가 실소스끼리 대조합니다.

### 3.6 저녁 6시 (요구 5)

```
✓ 일본 시각 18시 전에는 아무것도 하지 않는다
✓ 저녁은 2통 — 문제 1통, 답 1통
✓ 저녁은 일자를 진행시키지 않는다               advanceDay 호출 없음
✓ 저녁은 아침과 같은 날·같은 문법을 다룬다
```

아침 것을 그대로 다시 보내지 않고 **문제 형태**로 바꿔서 냅니다 —
한국어만 내고 답을 다음 통에 두어, 떠올리는 사이를 만듭니다.
대상은 진도에서 역산하지 않고 **오늘 아침 실제로 받은 사람**만
(`pushlogs.listReviewTargets`). 역산하면 오늘 못 받은 사람에게도
「배우지 않은 것의 복습」이 갑니다.

## 4. 아직 없는 것 — 체험이 끝난 뒤

**요구사항 「구독할 것인지 선택」의 결제 쪽이 통째로 없습니다.**

실측:

```
체험 3일을 다 쓴 사람에게, 4일째 아침
  결과            日数切れ
  보낸 메시지     없음
  남긴 기록       없음
  ✗ 아무것도 보내지 않고 기록도 남기지 않습니다

101일을 다 마친 사람에게, 다음 아침
  결과            修了済
  보낸 메시지     없음
  ✗ 수료 인사가 없습니다
```

근거:

| 있는 것 | 부르는 곳 |
|---|---|
| `billing.PACKAGES` (7/14/30/60/101일, 980〜7480엔) | 정의만 |
| `billing.creditPurchase` (재전송 방어 포함, 검증 완료) | **`smoke.mjs` 와 `verify-server.mjs` 뿐** |
| `push_logs.push_type = 'upsell'` | ENUM 에만 있음 |
| `push_logs.push_type = 'completion'` | ENUM 에만 있음 |
| `push_logs.push_type = 'quiz'` | ENUM 에만 있음 |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` | `.env.example` 에만 있음 |
| `app.mjs` 의 경로 | webhook / link start / callback / health — **결제 없음** |

즉 지금 상태로 공개하면 **모든 이용자가 3일 뒤에 조용히 멈춥니다.**
돈을 낼 방법도, 멈춘 이유를 알 방법도 없습니다.

`push-daily.mjs` 의 주석은 「切れた人は upsell の対象で、このバッチの担当ではない
（別の便で送る）」라고 적고 있는데, **그 「別の便」이 아직 없습니다.**

**여기서 멈춥니다.** 결제는 기술·서비스 선택(결제사, 결제 화면을 LIFF로 할지
웹으로 할지, 가격 표시 방식)이 필요하고 그건 대표님 몫입니다.
`docs/plan-billing.md` 가 이미 있으므로, 다음 단계는 그 계획서를 실제
코드베이스에 맞춰 갱신하는 일이 됩니다.

## 5. 관문에 넣은 회귀 검사 2건

같은 것이 다시 들어오지 않도록, **기존 관문**에 넣었습니다.
새 스크립트를 만들지 않은 것은, 늘리면 `deploy.yml` 에 등록을 잊는 경로가
하나 더 생기기 때문입니다.

| 검사 | 파일 | 무엇을 막는가 |
|---|---|---|
| 答えた段は、もう訊かない（次の段が返る） | `tools/verify-webhook.mjs` | §1 |
| 生年月日を飛ばした人にも、コースは訊く | `tools/verify-push.mjs` | §2 |

**이 두 검사가 실제로 버그를 잡는지 확인했습니다** — 수정을 되돌리면
둘 다 떨어지고, 되돌리기를 취소하면 둘 다 통과합니다.

```
수정을 되돌린 상태:
  ✗ 答えた段は、もう訊かない（次の段が返る）
  ✗ 生年月日を飛ばした人にも、コースは訊く — 예외로 낙하: 未知の track: null
원복 후:
  PASS webhook / PASS push
```

관문 16종 전체: **16 PASS / 0 FAIL**

## 6. 검증하지 못한 것 (정직하게 남김)

- **실물 LINE 왕복** — 채널 시크릿도 액세스 토큰도 없습니다. 서명 검증·
  push·reply 는 전부 가짜를 주입해 확인했습니다
- **실물 DB** — `repo/` 가 던지는 SQL 은 읽었지만, 본번 MySQL 에서 실제로
  통하는지는 `smoke.mjs` 를 서버에서 돌려야 압니다
- **cron 등록 여부** — `push-cron.sh` 는 있고 주석에 등록할 행도 적혀
  있지만, ChemiCloud 에 실제로 걸려 있는지는 접속하지 않아 모릅니다.
  `tools/cpanel.sh --api2 Cron/listcron` 으로 확인할 수 있습니다
- **원고** — `server/content/` 는 저장소에 없습니다. 위 실기에서는 조건
  (`checkLines`)을 만족하는 최소 문면을 만들어 주입했습니다. 실제 101일
  원고의 품질은 별개입니다
