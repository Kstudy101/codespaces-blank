## 2. 이 저장소의 실제 제약

```
index.html      진단 앱 본체 (CSS·JS 인라인, 자체 완결)
privacy.html    プライバシーポリシー
contact.html    お問い合わせ
tips.html       豆知識 (.tip 컴포넌트)
404.html
page.css        문서 페이지 3장이 공유
kanji.json      상용한자 2,136자 (지연 로딩)
```

- **빌드 도구 없음.** `package.json`도 번들러도 없다. `tools/build-site.sh`가 공개 파일을 `dist/`에 모으는 것이 전부
- **배포**: `main` push → GitHub Actions → rsync → Xserver. `tools/build-site.sh`의 `PUBLIC` 배열에 넣지 않은 파일은 배포되지 않음
- **`.htaccess`가 확장자 없는 URL을 처리**. 새 페이지 `omikuji.html`은 `/omikuji`로 접근됨 (별도 설정 불필요)
- **이미 갖고 있는 것** — 재활용 가능:
  - 자음오행 매핑 (`ㄱㄲㅋ→木` …) + 오행 설명 5종
  - 십이지(띠) 계산
  - 한자 → 한국 한자음·훈음 2,136자
  - 한자어 수사 변환 (`1995 → 천구백구십오`)
  - 받침 판정 → 조사 자동 선택
  - Canvas 공유 카드 생성 (1080×1350) + SNS 공유 경로

## 3. 사주 엔진 — KASI API가 필요 없는 이유

원안은 KASI에서 **일별 간지**를 받아 테이블로 만듭니다. 하지만 사주 4주는 성질이 다릅니다.

| 기둥 | 계산 방법 | 외부 데이터 필요? |
|---|---|---|
| **일주(日柱)** | 기준일로부터의 경과일 `% 60` | **불필요** — 순수 산술 |
| **연주(年柱)** | 입춘 경계로 연도 판정 후 `% 60` | 절기 시각만 필요 |
| **월주(月柱)** | 12절(節) 경계로 월 판정 | 절기 시각만 필요 |
| 시주(時柱) | 일간 + 시진 | 불필요 (진태양시 보정 시 경도 필요) |

즉 **필요한 외부 데이터는 24절기 시각뿐**입니다.

```
원안:   1930~2030 일별 간지   = 36,900행  ≈ 1.1MB (gzip 200KB)
개정:   1930~2030 절기 시각   =  2,424행  ≈  40KB (gzip 12KB)
```

절기 시각은 **태양황경이 15° 배수가 되는 순간**으로 정의되며 천문 계산으로 구합니다.
간이 VSOP87 수준이면 오차 1분 이내로, 절기 경계 판정에는 충분합니다.

### 산출물

```
tools/build-solar-terms.py   →   solar-terms.json
```

- 오프라인 계산. **API 키·시크릿·PR 검토 흐름 불필요**
- `tools/build-kanji-json.py`와 동일한 패턴(로컬 실행 → 결과 커밋)

### 검증 — 통과 (2026-08-01)

절기 시각과 **일주 기준일(epoch)** 은 틀리면 모든 결과가 어긋나므로, 구현 전에 먼저 확정하고 검증했습니다.

```
tools/fetch-naoj-reference.py  →  data/naoj-reference.json   (기준값 확보)
tools/verify-saju.mjs          →  20항목 전부 통과            (대조)
```

기준은 **일본 국립천문대 역계산실**입니다. 키·등록 없이 절기 시각·일간지·균시차를
모두 내주는 유일한 공표 창구였습니다. 결과는 커밋해 두므로 검증 때 통신하지 않습니다.

| 항목 | 실제로 한 것 | 결과 |
|---|---|---|
| 1 절기 시각 | 2009~2027 × 24절기 = **456건** | 최대 오차 **1분** (허용 ±2분) |
| 2 일주 기준일 | 연속 60일 × 9구간 = **540일** | 전건 일치 |
| 3 절 경계 월주 | 12절 × 19년 = **228곳**, 전후 10분 | 전부 정확히 1칸 진행 |
| 4 서머타임 경계 | 경계일 20일 × 5시각 = **100건** | UTC가 `Intl`과 일치 |
| 5 23시대 일주 | 4도시 × 3일 × 분단위 = **2,880건** | 전건 일치 (넘김 721건) |
| 6 경도 보정 | 서울 −32 / 부산 −24 / 도쿄 **+19** / 나하 −29분 | 부호·크기 일치 |

원안의 「서로 다른 만세력 3곳 × 20건」은 **국립천문대 연속 540일**로 대체했습니다.
만세력 사이트는 출처를 밝히지 않아 서로 독립인지 확인할 수 없는 반면, 연속 540일은
기준일이 하루라도 어긋나면 540건이 전부 틀어지므로 20건 표본보다 강한 검사입니다.

표준시·서머타임은 `Intl`(단말의 tz 데이터)과 대조합니다. `saju.js`가 실행 시 `Intl`을
부르지 않고 표를 구워 넣었기 때문에, 이건 서로 다른 두 출처를 비교한 것이 됩니다.
1930~2030을 6시간 간격으로 **295,120점** 대조해 전건 일치했습니다.

**검증이 잡아낸 것**

- **균시차의 부호가 반대였습니다.** `equationOfTime()`이 「평균 − 시(視)」를 돌려주고
  있었는데 호출부는 「시 − 평균」으로 쓰고 있었습니다. 최대 ±16.5분이므로 어긋남은
  최대 33분 — 2시간 단위인 시지(時支)를 경계에서 통째로 한 칸 밀어버립니다.
  국립천문대 값과 맞추지 않았으면 발견할 수 없었습니다 (크기는 맞고 부호만 틀리므로)
- **「1984-02-02 = 갑자일」은 사실이 아닙니다.** 공표값으로 그날은 **병인(丙寅)** 이고
  갑자일은 **1984-01-31** 입니다. 1984년이 갑자「년」인 것과 뒤섞인 설로 보입니다.
  덧붙여 그 갑자년의 시작(입춘)도 흔히 쓰는 02-04가 아니라 **한국시간 02-05 00:19**
  입니다. 같은 착각으로 기준일을 이틀 밀지 않도록 틀린 쪽도 함께 못박아 두었습니다

### 시주(時柱) — 포함 확정

**결정: 포함한다.** 다만 비용을 정확히 알고 시작해야 합니다.

시주는 「일간 + 시진」이라는 단순한 표 조회로 끝나지 않습니다. 정확히 하려면 세 가지가 붙습니다.

| 보정 | 내용 | 검증 난이도 |
|---|---|---|
| **진태양시** | 출생지 경도와 표준자오선(135°E)의 시차. 서울 기준 약 −32분 | 중 — 도시별 경도 표 필요 |
| **서머타임** | 한국 1948~51, 1955~60, 1987~88년 시행. 해당 기간 출생자는 1시간 보정 | 낮 — 기간 표 내장 |
| **조자시/야자시** | 23:00~24:00을 당일로 볼지 다음날로 볼지. 유파에 따라 다름 | 낮 — 옵션 플래그 |

**설계 방침**

- 시주 로직을 **별도 파일로 분리**합니다. 계산 오류가 나도 연·월·일주는 영향받지 않도록
- 출생 시각을 **모르는 사용자가 다수**입니다. 「시간 모름」 선택지를 반드시 두고,
  선택 시 시주를 빼고 3주로 계산 + 화면에 그 사실을 표시
- 진태양시 보정은 **주요 도시 목록 선택**으로 처리(경도 직접 입력 없음).
  일본 거주자가 대부분이므로 일본 도시도 포함해야 합니다 — 도쿄(139.7°E)는 +19분으로
  한국과 부호가 반대입니다
- 조자시/야자시는 기본값을 하나 정해 고정하고, 옵션 노출은 하지 않습니다
  (일반 사용자에게 설명 불가능한 선택지)

**추가 검증 항목 4~6도 통과했습니다** — 위 표 참조. 조자시/야자시는 **조자시로 고정**
(진태양시 23:00부터 다음 날)했고, 화면에 옵션으로 내보내지 않습니다.

## 4. 저장 정책 — 결정과 그로 인해 생긴 충돌

**결정: 생년월일은 A(저장하지 않음). 단어장·출석은 만든다.**

이 두 결정은 그대로는 양립하지 않습니다. 단어장과 출석 스탬프는 **저장이 있어야
존재할 수 있는 기능**이기 때문입니다. 어제 모은 단어가 사라지는 단어장, 연속 일수가
초기화되는 출석부는 기능이라 부를 수 없습니다.

### 해석 — 무엇을 지키려는 약속인가

이 사이트의 프라이버시 문구가 지키려는 것은 **입력된 개인정보**입니다.

> 「入力されたお名前・生年月日は保存されません」

이름과 생년월일은 개인을 특정할 수 있는 정보이고, 일본인 사용자가 입력을 망설이는
대상입니다. 반면 **사용자가 스스로 모은 한국어 단어 목록**과 **방문한 날짜**는
성격이 다릅니다. 학습 이력이지 신원 정보가 아닙니다.

따라서 다음과 같이 나눕니다.

| 데이터 | 저장 | 근거 |
|---|---|---|
| 이름·후리가나 | **저장 안 함** | 개인 식별 정보. 현 약속 유지 |
| 생년월일·출생시각 | **저장 안 함** (A) | 동일 |
| 단어장(모은 단어) | 기기에 저장 | 학습 이력. 사용자가 명시적으로 「저장」을 누른 것만 |
| 출석 기록(날짜 목록) | 기기에 저장 | 학습 이력 |

### 폴리시를 반드시 고쳐야 합니다

현재 문구는 **뭉뚱그린 부정**이라 이 구분을 담을 수 없습니다.

```
현재 (privacy.html 1항):
  「Cookie・localStorage 等への保存も行いません」   ← 단어장을 만드는 순간 거짓
```

→ 대상을 명시하는 문구로 바꿉니다.

```
개정안:
  診断機能に入力されたお名前・ふりがな・生年月日は、保存されません。
  一方、単語帳に保存された単語と出席の記録は、お使いの端末（ブラウザ）の中に
  保存されます。これらはサーバーへ送信されず、運営者が見ることはできません。
  「保存した単語をすべて削除」からいつでも消去できます。
```

**전량 삭제 버튼은 필수입니다.** 저장한다고 적어놓고 지울 방법을 주지 않으면
약속의 절반만 지키는 것이 됩니다.

> GA4·Clarity 때와 같은 패턴입니다 — 저장 기능을 넣는 커밋에서 폴리시를 함께
> 고치지 않으면, 폴리시가 그 순간부터 거짓 문서가 됩니다.

### 「어제와 비교」는 A를 지킨 채로 가능합니다 (정정)

앞선 판단에서 「어제와 비교하려면 생년월일을 저장해야 하므로 A와 충돌한다」고 적었으나,
**이는 틀렸습니다.** 비교에 필요한 것은 어제의 **점수**이지 생년월일이 아닙니다.

```
오늘 방문 → 생년월일 입력(저장 안 함) → 오늘 점수 계산
                                          ↓
                        어제 저장해 둔 점수와 비교해서 ↑↓ 표시
                                          ↓
                              오늘 점수를 저장 (생년월일은 버림)
```

실제로 저장되는 형태입니다(구현 완료). **생년월일이 들어가지 않습니다.**

```js
// localStorage: "k101.fortune"   — 101 바이트
{
  v: 1,
  prev: { d: "2026-07-28", s: [40, 52, 55, 65, 58, 36] },
  cur:  { d: "2026-08-01", s: [50, 52, 55, 65, 58, 36] }
}
// s 의 순서는 총운·재물·연애·사업·건강·학업 (Fortune.CATS 순)
```

두 회분을 갖는 이유는, 같은 날 여러 번 열어도 「전회」가 밀려나지 않게 하기 위해서입니다.
한 회분만 두면 오늘 두 번째로 열었을 때 전회가 오늘 것으로 덮여 비교가 사라집니다.
키 이름을 항목별 객체가 아니라 배열로 둔 것은 용량 때문이고, 순서는 코드가 정합니다.

점수는 계산 결과이므로 이것만으로는 생년월일을 알 수 없고, 개인을 특정할 수도 없습니다.
따라서 **A(이름·생년월일 저장 안 함)를 그대로 유지하면서 비교 기능이 성립합니다.**

> **생년월일 해시를 저장하는 방식은 쓰지 않습니다.** 「같은 사람인지 확인」하려고
> 생년월일 해시를 저장하는 설계가 흔하지만, 생년월일시의 경우의 수는
> 약 5,200만 가지에 불과해 **해시를 전수 대입으로 되돌릴 수 있습니다.**
> 저장하지 않겠다는 약속을 사실상 깨는 것이므로 채택하지 않습니다.

**대신 라벨을 정직하게 붙입니다.** 동일인 여부를 확인하지 않으므로
「あなたの昨日」가 아니라 **「前回の結果と比べて」**로 표기합니다.
다른 생년월일을 넣으면 비교 대상이 어긋나지만, 그것은 사용자가 아는 상태입니다.

### 남은 마찰 — 매일 입력

비교 기능은 해결됐지만, **매일 생년월일시 5개 필드를 다시 입력**하는 마찰은 남습니다.

| 안 | 내용 |
|---|---|
| **A 그대로** | 매번 입력. 약속이 가장 강함 |
| **A + 옵트인** | 기본은 저장 안 함. 「この端末に記憶する」를 사용자가 켰을 때만 |

기능상으로는 A 그대로도 전부 동작합니다. 옵트인은 **편의성만**의 문제로 축소됐습니다.

## 5. 페이지 구성

## 6-1. 운세 점수 모델 — 비교의 대상

「어제보다 ↑」를 보여주려면 **비교 가능한 수치**가 있어야 합니다. 문장만으로는 비교되지 않습니다.

### 항목

학습 사이트이므로 **학업운을 포함**합니다. 다른 운세 사이트에는 잘 없고,
이 사이트의 정체성(한국어 학습)과 직접 이어집니다.

| 항목 | 일본어 | 오행 대응 |
|---|---|---|
| 총운 | 総合運 | 전체 균형 |
| 재물운 | 金運 | 金 |
| 연애운 | 恋愛運 | 水 |
| 사업운 | 仕事運 | 木 |
| 건강운 | 健康運 | 土 |
| **학업운** | 学習運 | 火 |

### 산출 방식

**오늘의 일진(日辰) 오행**과 **사용자 사주의 오행 분포**를 상생·상극으로 대조합니다.

```
오늘의 일진 → 천간·지지 → 오행
사용자 사주 → 연·월·일·시주 → 오행 분포 (부족/과다)

상생(生): 오늘의 오행이 내 부족한 오행을 채워줌  → 점수 ↑
상극(剋): 오늘의 오행이 내 과다한 오행을 누름     → 점수 ↑ (균형)
          오늘의 오행이 내 부족한 오행을 더 누름   → 점수 ↓
```

- **결정론적**입니다. 같은 생년월일 + 같은 날짜면 항상 같은 결과.
  난수를 쓰면 새로고침으로 점수가 바뀌어 비교가 무의미해집니다
- 0~100 정수. 표시는 5단계 등급(大吉/吉/中吉/小吉/末吉)과 병기
- 날짜가 바뀌면 일진이 바뀌므로 **매일 자연스럽게 달라집니다**

### 비교 표시

```
今日の運勢                    前回（7/30）と比べて
─────────────────────────────────────────
総合運   72  中吉             ↑ +10
金運     40  末吉             ↓ −22
恋愛運   78  吉               ↑ +3
仕事運   55  小吉             →  0
健康運   71  中吉             ↑ +16
学習運   66  中吉             ↓ −4
```

- 첫 방문(비교 대상 없음)에는 비교 열을 감추고 「明日また来ると、変化がわかります」 안내
- 하루를 건너뛰면 「前回（7/28）」처럼 **실제 날짜를 표시**합니다.
  「어제」라고 단정하면 거짓이 됩니다

### 학습 연결

**학습운이 낮은 날 → 「그래도 한 단어만」** 으로 유도합니다.
운세가 나쁘다고 끝내지 않고 작은 행동을 제안하는 것이,
학습 사이트로서 이 콘텐츠를 두는 이유입니다.

## 7. 몰입 구조 — 오늘의 운세를 입구로

**결정: 오늘의 운세를 먼저 만들고, 거기서 다른 콘텐츠로 끌고 간다.**

### 의존 관계 — 순서가 강제됩니다

오늘의 운세는 사주 기반이므로 **계산 엔진이 먼저**입니다. 검증되지 않은 계산 위에
입구 기능을 얹으면, 나중에 계산을 고칠 때 입구부터 다시 만들게 됩니다.

```
절기·일주 검증 통과  →  오늘의 운세  →  길방 · 부적
                          │
                          └─ 오미쿠지 (엔진 불필요, 언제든 병행 가능)
```

### 하루의 동선

매일 돌아오게 만드는 것이 목표이므로, **하루에 한 번 완결되는 고리**를 만듭니다.

```
① 홈 상단 「오늘의 운세」
   생년월일시 입력 → 오늘의 총운·재물·애정·건강
        ↓  결과 문구에서 핵심 어휘 3~5개
② 어휘 카드 — 뜻풀이 · 발음 재생 · 「단어장에 저장」
        ↓
③ 출석 스탬프 적립 — 「연속 N일」 표시
        ↓  다음 행동 제안 (오늘 운세 내용에 맞춰 분기)
④ ・재물운이 낮다  → 「부적을 만들어 보세요」   → /amulet
   ・이동운이 좋다  → 「오늘의 길한 방위는?」    → /gilbang
   ・가볍게 한 번 더 → 「오미쿠지를 뽑아보세요」  → /omikuji
```

**④의 분기가 핵심입니다.** 모든 사용자에게 같은 링크를 나열하면 그냥 메뉴지만,
**오늘의 결과에 맞춰 다른 것을 권하면** 이어서 볼 이유가 생깁니다.

### 몰입을 만드는 장치

| 장치 | 내용 | 근거 |
|---|---|---|
| **하루 1회 제한** | 오늘의 운세·오미쿠지는 하루 한 번 | 다시 뽑을 수 있으면 결과의 무게가 사라짐 |
| **연속 일수** | 「3일 연속」 표시 | 끊기 아까움이 재방문 동기 |
| **전회와 비교** | 6항목 전부 증감 표시 | 다시 온 사람에게만 보이는 정보 (§6-1) |
| **단어 누적** | 「지금까지 42단어」 | 학습 성과의 가시화 |
| **미완성 표시** | 「오늘 아직 안 뽑은 것: 오미쿠지」 | 마무리하고 싶게 만듦 |

> 이 장치들은 **전부 A를 유지한 채로 구현 가능**합니다(§4 정정 참고).
> 저장되는 것은 날짜 목록과 점수뿐이고, 생년월일은 들어가지 않습니다.
> 「前回と比べて」의 항목별 증감은 §6-1의 점수 모델을 씁니다.

- **`words.html`은 `noindex`이고 sitemap에 넣지 않았습니다.** 정적 해설(받침·한자어)은
  넣었지만 본체가 단말별 목록이라 크롤러에게는 늘 비어 보입니다. AdSense 심사에서
  빈 페이지로 보이는 문제를 한 번 겪은 사이트라, 색인시키지 않는 편이 안전합니다.

- **`study.js`는 받침 판정을 자체 구현합니다.** `index.html`에도 같은 판정이 있지만
  인라인이라 `words.html`에서 부를 수 없습니다. 한글은 규칙적으로 배열돼 있어
  자모 분해 없이 `(코드 − 0xAC00) % 28`로 나옵니다

**저장 실패를 삼키지 않습니다**

`add()`는 `added` / `duplicate` / `full` / `failed`를 돌려주고 화면이 각각 다르게 반응합니다.
「저장했다고 했는데 안 들어간」 상태가 조용히 생기지 않도록 한 것이고, 검증이
용량 초과를 실제로 재현해 `failed`가 나오는지 확인합니다.

**2-A에서 정해진 것**

- **하루 1회 제한은 두지 않습니다.** 점수가 결정론적이라 다시 눌러도 같은 값이 나옵니다.

- **「오늘」은 단말의 달력 날짜** 기준입니다. 일주는 진태양시 23시에 넘어가지만
  그건 태어난 순간의 이야기고, 화면의 「오늘」은 사용자가 오늘이라고 여기는 날과
  같아야 날짜 표시가 어긋나지 않습니다
- **띠 표기는 STEP 6을 그대로 두고**, 입춘 기준과 갈리는 생일에만 각주를 답니다.
  한 페이지에서 말띠와 뱀띠가 동시에 나오는 것을 막으면서, 라이브 출력은 바꾸지 않습니다

```
tools/verify-omikuji.mjs   15항목 통과 (배포 관문에 연결)
```

**운세와 일부러 반대로 만들었습니다**

| | 오늘의 운세 | 오미쿠지 |
|---|---|---|
| 결정 방식 | 사주로 계산 (결정론) | 그 자리 추첨 (무작위) |
| 다시 하면 | 같은 값 | 다른 값 → **그래서 하루 1회 제한** |
| 검증 항목 | 「눌러도 안 바뀌는가」 | 「뽑을 때마다 바뀌는가」 |

이 대비가 그대로 페이지의 정적 콘텐츠가 됩니다. 오미쿠지는 뽑는 점, 토정비결은
생년월일로 괘를 정하는 점 — 「뽑는 점」과 「계산하는 점」의 차이이고,
이 사이트의 오늘의 운세는 토정비결 쪽에 속한다는 설명으로 이어집니다.

**본문은 실재하는 속담(속담 15개)입니다.** 지어낸 점괘 문구가 아니라
「천 리 길도 한 걸음부터」처럼 일본어와 대응하는 것을 골랐습니다. 등급의 논조와
3조로 나눠 둬서 대길에 「소 잃고 외양간 고친다」가 나오지 않습니다 — 검증이
이 조합을 이름을 대고 확인합니다.

**`/omikuji`는 sitemap에 넣었습니다.** `/words`와 반대 판단인데, 이쪽은 본체가
정적 해설(1,350자)이고 크롤러가 읽을 것이 실제로 있기 때문입니다.

**4단계 — 길방 — 완료 (2026-08-01)**

```
tools/build-new-moons.py   →  new-moons.json  (삭 507건, 1.6KB)
gilbang.js                    恵方 · 손없는 날 · 오행 방위
gilbang.html                  /gilbang
index.html                    사업운 60 이상이면 길방 권유 (§7 ④)
tools/verify-gilbang.mjs      15항목 통과 (배포 관문에 연결)
```

**손없는 날을 계산할 수 있게 됐습니다**

한국 방위 관습에서 가장 특징적인 것이고, 음력 일자의 끝자리로 손(厄)이 있는
방향이 정해집니다(9·0일은 손이 없어 어디든 좋음). 음력이 필요해 처음엔 접으려
했지만, 필요한 것이 **음력 「일」뿐**이라는 점이 열쇠였습니다 — 음력에서 가장
까다로운 윤달 배치는 「월」의 번호에만 영향을 주므로, 삭(朔) 날짜만 있으면 됩니다.

국립천문대 `phenomena_p.cgi`가 삭을 공표합니다(2009~2027). **235건 전건 일치**로
검증했습니다. 삭이 하루라도 어긋나면 방위가 통째로 한 단 밀리므로, 여기가 이 페이지의
급소입니다.

| | 恵方 | 손없는 날 | 오행 방위 |
|---|---|---|---|
| 결정 | 연간(年干) | 음력 일자 | 사주 + 일진 |
| 주기 | 1년 (입춘 기준) | 5일마다 이동 | 사람마다 / 날마다 |
| 대상 | 전원 동일 | 전원 동일 | 개인별 |
| 성격 | **향할 방향** | **피할 방향** | 보충할 방향 |

**恵方와 손없는 날은 방향을 가리키는 부호가 반대입니다** — 하나는 좋은 쪽,
하나는 나쁜 쪽. 이 대비가 페이지의 정적 콘텐츠(1,441자)가 됩니다.

**생년월일 없이도 절반이 동작합니다.** 恵方와 손없는 날, 오늘의 오행 방위는
입력이 필요 없어 페이지를 열면 바로 보입니다. 개인 길방만 선택 입력입니다.

**`new-moons.json`의 범위는 2000~2040**으로, 사주(1930~2030)와 다릅니다.
이 기능은 「오늘」과 가까운 미래(이사 날짜)에만 쓰이므로 과거로 거슬러 갈 이유가
없습니다. 검증이 「표가 오늘을 포함하는가」와 「남은 연수」를 확인하므로,
2038년쯤 되면 관문이 먼저 알려줍니다.

**5단계 — 부적 메이커 — 완료 (2026-08-01)**

```
amulet.js                6종 + 오방색 + 발원문 (저장·날짜 없음)
amulet.html              /amulet · 캔버스 부적 + 문화 비교 해설
index.html               금운 45 미만이면 부적 권유 (§7 ④)
tools/verify-amulet.mjs    28항목 통과 (배포 관문에 연결)
```

폰트는 **시스템 명조로 시작**했습니다. 외부 폰트 요청은 0건 그대로이고,
캘리그래피 웹폰트를 유료 API로 얹는 구상은 서버가 필요하므로 별도 스코프입니다.

**여기만 「바깥의 정답」이 있었습니다**

부적에는 맞춰볼 수치가 없습니다. 절기(국립천문대)나 삭(朔)처럼 대조할 공표값이
없고, 오방색·방위 대응은 언전대로의 표뿐입니다. 대신 이 페이지에는 다른
페이지에 없는 것이 하나 있습니다 — **한자**.

이 사이트는 이미 상용한자 2,136자의 한국 한자음·훈음을 갖고 있습니다(`kanji.json`).
부적 한가운데 놓는 글자의 음이 틀리면 그건 장식의 오류가 아니라 **교재의 오류**이므로,
12자(중앙 6 + 칙령 2 + 오행 5 + 오방색 5 중 중복 제외)를 1자씩 대조합니다.

**정자/신자체가 갈리는 글자는 쓰지 않습니다.** 한국의 부적은 정자로 쓰므로
`学(學)`이나 `縁(緣)`을 놓으면 화면과 실물이 다른 글자가 됩니다. 검증이
`kanji.json`의 구자체 표로 기계적으로 확인하되, **호환한자는 구분합니다** —
`福`에는 U+FA1B가 있지만 이건 자형이 갈린 것이 아니라 부호화의 사정이고
한국에서도 일본에서도 쓰는 형태는 같은 `福`(U+798F)입니다. 규칙이 헛돌지 않는지는
`學→学`·`緣→縁`이 실제로 걸리는지로 확인합니다.

| | 오늘의 운세 | 오미쿠지 | 길방 | 부적 |
|---|---|---|---|---|
| 바뀌는 주기 | 매일 | 하루 1회 추첨 | 날·해 | **바뀌지 않음** |
| 근거 | 사주 × 일진 | 난수 | 연간·음력일 | 소원(+사주) |
| 저장 | 점수 2회분 | 당일 결과 | 없음 | **없음** |

**부적은 날짜를 갖지 않습니다.** 원래 1년 지니고 정월에 새로 하는 것이라
「오늘의 부적」으로 만들면 매일 다시 만드는 물건이 되어 성격이 바뀝니다.
검증이 `amulet.js`에 `Date`와 `Math.random`이 나오지 않는 것으로 담보합니다.

**저장을 하지 않으므로 `privacy.html`은 고치지 않았습니다.** 저장 4종 그대로입니다.
지금까지는 기능을 넣을 때마다 폴리시를 같은 커밋에서 고쳐 왔는데, 이번엔
고칠 것이 없다는 쪽이 맞습니다 — 검증이 `localStorage`·쿠키 부재를 확인하므로,
나중에 저장이 생기면 **폴리시보다 먼저 관문이 떨어집니다**.

**5단계에서 정해진 것**

- **오행↔항목은 `fortune.js`, 오행↔방위는 `gilbang.js`가 이미 정했습니다.**
  세 번째 사본을 만들지 않고 그쪽을 부릅니다(부족 오행 판정은 `Gilbang.mine`).
  검증이 6항목 전부를 `Fortune.CATS`와 1:1로 대조합니다 — 어긋나면
  「금운 부적이 수(水) 오행」 같은 것이 조용히 생깁니다
- **색은 전통 쪽을 고정했습니다.** 황지에 주서(朱書)는 관습 그대로 두고,
  오행별로 종이 색을 바꾸지 않습니다. 오방색은 아래 귀퉁이 **인(印)에만** 넣고,
  그 부분은 「이 사이트가 정한 것」이라고 화면에 적었습니다
- **소원 선택이 사주 추천을 덮어쓰지 않습니다.** 부족 오행을 「▲ 추천」으로
  표시할 뿐이고, 무엇을 빌지는 본인이 정하는 것이지 계산이 정할 일이 아닙니다
- **발원문은 「-소서」로 통일했습니다.** 기원을 나타내는 고어 종결어미로,
  현대 회화에는 안 나오지만 기도문·가사에 남아 있습니다. 조사(을/를·이/가)는
  `study.js`의 받침 판정으로 되짚어 검사합니다
- **`/amulet`은 sitemap에 넣었습니다.** 정적 해설이 2,549자로 `/omikuji`와
  같은 판단입니다. 홈의 분기는 **1본만** 냅니다 — 두 개를 늘어놓으면 메뉴로 돌아갑니다

**분기의 실제 출현율** (400인 × 30일 = 12,000회)

| 분기 | 조건 | 출현 |
|---|---|---|
| 부적을 권함 | 금운 < 45 | 28.9% |
| 길방을 권함 | 위에 해당 없고 사업운 ≥ 60 | 12.4% |
| 아무것도 안 냄 | — | 58.7% |

부적을 먼저 보므로 길방은 19.6% → 12.4%로 7.2포인트를 양보합니다. 그래도
**절반 이상은 아무것도 나오지 않습니다** — 늘 떠 있으면 「오늘의 결과에 맞춘
제안」이 아니라 고정 메뉴가 되기 때문에, 이건 줄일 것이 아니라 지킬 쪽입니다.

**캔버스는 stub으로 실제로 돌려서 봤습니다**

부적은 이미지라 어긋나도 눈으로만 알 수 있습니다. 이 저장소엔 jsdom이 없으므로
(`package.json` 자체가 없음) 기록만 하는 canvas와 최소한의 DOM을 세워
`amulet.html`의 `draw()`를 그대로 실행하고, 6종 전부에 대해 **문자 77건이
주(朱) 안쪽 테두리에 들어가는지**와 **가운데로 쌓은 행이 겹치지 않는지**를 봅니다.
글자 폭은 개산(概算)이므로 특정 단말의 픽셀 위치를 보증하는 것이 아니라,
길어졌을 때 줄이는 처리가 살아 있는지를 봅니다 — 25자짜리 소원을 실제로
넣어 확인합니다.

## 8. 남은 결정

1. **「A + 옵트인」을 채택할지** (§4) — **기능 문제가 아니라 편의성 문제로 축소됐습니다.**
   비교·연속일수·단어장은 A 그대로도 전부 동작합니다. 옵트인은 매일 5개 필드를
   다시 입력하는 마찰만 없애줍니다
> 조자시/야자시는 **결정됐습니다** — 조자시(진태양시 23:00부터 다음 날)로 고정,
> 옵션 노출 없음. `saju.js`에 구현·검증까지 끝났습니다 (§3).

> **하루 1회 제한의 리셋 시각도 결정됐습니다** — **단말의 달력 날짜(로컬 자정)**.
> KST와 JST는 둘 다 UTC+9이므로 주 이용자층에게는 차이가 없고, 로컬 쪽이
> 「사용자가 오늘이라고 여기는 날」과 어긋나지 않습니다. 운세·오미쿠지·출석이
> 모두 같은 구분을 씁니다 — 하나만 다르면 운세는 오늘 것, 오미쿠지는 어제 것이
> 되는 날이 생깁니다.
>
> 제한 자체가 필요한 것은 **오미쿠지뿐**입니다. 운세는 결정론적이라 다시 눌러도
> 같은 값이 나와 제한할 것이 없지만, 오미쿠지는 무작위라 막지 않으면
> 「좋은 게 나올 때까지」가 됩니다(§7).

## 10. 원안 대비 요약

- **KASI API·시크릿·전용 워크플로 — 불필요.** 절기 시각만 있으면 되고 오프라인 계산 가능
- **테이블 용량 1/20** (gzip 200KB → 12KB)
- **저장 범위를 나눔** — 이름·생년월일은 저장 안 함(A), 단어장·출석은 저장.
  **폴리시를 같은 커밋에서 개정해야 함**
- **시주 포함 확정** — 진태양시·서머타임·조자시 보정 포함. 「시간 모름」 선택지 필수,
  검증 항목 3종 추가
- **학습 모듈 전부 신규** — `study.js` 공용 파일로. 발음은 `SpeechSynthesis`(외부 요청 0)
- **오늘의 운세를 입구로** — 결과에 따라 다음 콘텐츠를 분기 제안하는 구조
- **6항목 점수 + 전회 비교** — 총운·재물·연애·사업·건강·**학업**.
  점수만 저장하므로 A를 지킨 채 비교가 성립. 생년월일 해시 저장은 채택하지 않음
  (전수 대입으로 복원 가능하므로 약속을 깨는 것과 같음)
- **부적 폰트는 시스템 폰트로 시작** — 유료 고품질은 서버가 필요하므로 별도 스코프.
  부적은 저장도 날짜도 갖지 않고, 한자음은 이미 가진 `kanji.json`과 대조
- 문화 비교·역할 구분·어휘 스키마 등 **원안의 콘텐츠 설계는 대부분 그대로 유효**

## 11. LINE 배포 서버 (ChemiCloud) — 신설

**결정: ChemiCloud 를 사용한다.** §0 의 「백엔드를 쓰지 않는다」는 더 이상 유효하지 않습니다.

조사 결과는 [research.md](research.md) 에 있습니다. 여기에는 **계획**만 적습니다.

### 11.1 현재 상태

이미 만들어져 있으나 **커밋되지 않았습니다** (약 2,900행).

```
server/                       28개 파일. Node ≥20, 의존성은 mysql2 하나
  app.mjs                     /webhook · /link/start · /link/callback · /health
  db/schema.sql               MySQL 9 테이블
tools/verify-{server,webhook,onboarding}.mjs   1,932행
index.html                    +159행 (LINE 유도 섹션, 게이트 잠김)
deploy.yml                    +62행 (검증 3종 등록)
```

### 11.2 ⚠️ 착수 조건 — 폴리시 개정이 먼저입니다

`privacy.html` 1항은 지금 **「お名前・ふりがな・生年月日・出生時刻・出生地は
サーバーに送信されず、保存もされません」** 라고 단언합니다.
LINE 연동은 그 8개 항목을 실제로 MySQL 에 넣습니다.

**지금은 안전합니다** — `LINE_LINK_API = ''` 게이트가 카드를 감추고 있고,
그 코드 자체가 미배포입니다. 위험한 것은 **그 한 줄에 URL 을 넣는 순간**입니다.

```
LINE_LINK_API = 'https://api.kstudy101.jp'   ← 이 줄과
privacy.html 개정                             ← 이 개정은 반드시 같은 커밋
```

폴리시는 **사이트와 LINE 을 나누어** 쓰면 양쪽 다 사실이 됩니다.

```
개정 방향(초안):
  1항 サイトの診断機能   … 送信されず、保存もされません        (현행 유지)
  N항 LINE 配信サービス  … 連携ボタンを押した場合にかぎり、
                          お名前・生年月日等をサーバーに保存します
                          保存先・保存期間・削除方法・退会方法を明記
```

- **삭제·탈퇴 경로가 필수입니다.** 저장한다고 적고 지울 방법을 주지 않으면 약속의 절반만 지키는 것 —
  단어장 때와 같은 기준
- LINE 은 `line_user_id` 라는 **영구 식별자**를 다룹니다. 단어장(로컬 저장)과 성질이 다르므로
  같은 문단에 묶지 말 것

### 11.3 커밋 범위 — 결정 필요

`server/` 를 커밋하면 **공개 저장소에 들어갑니다.**

| | 공개됨 | 공개 안 됨 |
|---|---|---|
| 스키마·핸들러·repo 로직 | ✅ | |
| `.env.example` (빈 껍데기) | ✅ | |
| `.env` / `server/.env.local` | | `.gitignore` 로 제외 확인 |

스키마가 공개되어 곤란한지 판단이 필요합니다. 곤란하다면 별도 비공개 저장소로 분리해야
하고, 그 경우 `tools/verify-{server,webhook,onboarding}.mjs` 도 함께 옮겨야 합니다
(현재는 `server/` 를 참조).

### 11.4 배포 경로 — 사이트와 분리

```
정적 사이트  main push → Actions → build-site.sh → rsync → Xserver
LINE 서버    ?                                            → ChemiCloud
```

**Xserver 파이프라인에 섞지 않습니다.** `build-site.sh` 의 `PUBLIC` 배열은 화이트리스트라
`server/` 가 자동으로 배포될 일은 없지만, 반대로 **서버 배포 수단은 아직 없습니다.**

정해야 할 것:
- ChemiCloud 접속 방식 (SSH / Git / 패널) 과 기동 방식 (PM2? systemd? Passenger?)
- API 도메인 (`api.kstudy101.jp` ?) 과 SSL
- 환경변수 주입 방법 — `server/.env.example` 항목 전수 확인 필요
- LINE 채널 시크릿·액세스 토큰의 보관 위치

### 11.5 유료 과금 — 별도 검토

`purchases` 에 `7days/14days/30days/60days/101days`, `subscriptions` 에 3일 무료 체험이
들어 있습니다. **계획서 어디에도 과금 설계가 없습니다.**

과금은 특정상거래법 표기·환불 규정·결제 사업자 심사가 따라오므로,
**LINE 배포(무료) 와 과금은 분리해서 순서를 잡는 것**을 권합니다.

### 11.6 착수 순서 (제안)

```
① 폴리시 개정 초안 작성 → 검토 → 확정          ← 코드보다 먼저
② server/ 커밋 범위 결정 (공개 / 비공개 분리)
③ ChemiCloud 배포 경로 확립 + /health 확인
④ 검증 3종을 워크플로에 등록 (deploy.yml +62행 커밋)
⑤ LINE_LINK_API 에 URL 투입 ← ①과 같은 커밋이거나 그 이후
⑥ 과금은 별도 계획서
```

### 11.7 아직 안 읽은 것

`server/lib/**` 의 내부 로직(핸들러·repo)과 `.env.example` 전문은 조사하지 않았습니다.
②~③ 착수 전에 읽어야 합니다.
