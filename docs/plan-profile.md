## 1. 조사 — 이미 있는 것

- **인증**: `linelogin.mjs` 의 OAuth 전체(state 1회용·해시 저장·30분 만료)가 연동에서 가동 중.
  편집도 같은 경로를 타되 콜백의 「용도」만 구분 (연동 state 와 편집 state 를 섞으면
  연동 대기건이 편집으로 소비되는 사고 — state 발급 시 purpose 를 함께 저장)
- **gender 열은 이미 있습니다** — `saju_profiles.gender` 는 base schema 부터 존재,
  기본 `'U'`(未回答). privacy 도 「未回答を表す値だけをお送りし」로 그 사실을 공개 중.
  **004 의 일은 열 추가가 아니라 「실제 값을 받기 시작하는 것」** — ENUM 정의가
  실값('M'/'F' 등)을 허용하는지 확인·정비가 전부일 수 있음 (구조 변경 최소)
- **저장 경로**: `users.updateName` / `users.upsertSajuProfile` 재사용.
  upsert 는 생년월일 변경 시 `birth_confirmed` 를 자동으로 내리므로(기존 동작),
  편집으로 생년월일을 바꾸면 다음 접점에서 ②확인이 자연히 다시 나옴 — 원하는 동작
- **이름**: `kana2hangul.mjs` + Phase 1 의 확정 흐름 재사용 (§0.5 — name_kr 정본,
  변경 시에만 かな 재입력 → 변환 → 미리보기 → 확정)

## 2. 설계 개요

```
LINE 리치메뉴/「情報を変更」 → GET /profile/start → LINE Login (state, purpose=edit)
 → callback → 세션 쿠키(단명, HttpOnly) → GET /profile : 현재값 프리필 폼
 → POST /profile : 검증 → updateName / upsertSajuProfile → LINE 확인 1통
 → 사주·운세는 다음 아침 배신부터 자동 반영 (매일 프로필에서 계산)
    name_kr 변경은 그날 저녁 복습·다음 아침부터 즉시 반영
```

- 페이지는 `server/` 가 렌더 (`pages.mjs` 패턴). 사이트(dist) 쪽은 **무변경** —
  「사이트 폼 불변」 지시와, 페이지 추가 시 4곳 수정 함정을 둘 다 회피
- 프리필: 인증된 user_id 로 `users`+`saju_profiles` 로드. **빈 폼 재입력 금지가 존재 이유**
- 검증: 생년월일은 사이트와 같은 범위(1930~2030, 절기표와 동일), 시간은 임의,
  출생지는 기존 형식. 이름 변경은 かな만 (Phase 1 과 동일 규칙)

## 3. migration 004 (002 교훈 반영)

- 실상 확인 먼저: 본번 `SHOW CREATE TABLE saju_profiles` 로 gender ENUM 현황

# 6. A4 결정 자료 — gender 를 대운에 반영할 것인가 (2026-08-07 실측)

> 이 절은 **대표님이 한 줄로 답하시기 위한 자료**입니다. 코드는 쓰지 않았습니다.
> 위 §1~§5 는 2026-08-05 작성분이라 아래 실측과 어긋나는 곳이 있습니다 — 어긋난 곳은 §6-1 에.

## 6-1 먼저: 전제 2건 중 1건은 이미 끝났고, 1건은 성격이 달랐습니다

| 머리말의 전제 | 2026-08-07 실측 |
|---|---|
| ② privacy 문안 확정·게시 | **완료.** `c11242f` 「privacy 확정판」이 성별 행·본문 단락을 게시했고, `verify-onboarding` 이 문구 3개를 관문으로 강제 중(625행 부근) |
| §3 「migration 004 로 gender 정비」 | **끝났고 번호도 다릅니다.** `005-gender-not-answered.sql` 이 `ENUM('M','F','U','N')` 으로 확장 — `'U'`(안 물음)와 `'N'`(답하지 않겠다고 답함)을 분리 |
| §1 「gender 는 저장만」 | **수집도 이미 가동 중.** LINE 온보딩 `bgender` 단계가 3택(男性/女性/答えない)으로 실제 값을 받고 있습니다 (`onboarding.mjs` 568~575) |
| ① 대운 반영 여부 | **미결. 아래가 그 자료입니다** |

즉 **A4 는 1건**이고, B1(프로필 편집)은 그 1건과 사실상 독립입니다 — §6-5.

## 6-2 ★ 핵심 — 「반영」은 스위치가 아니라 신규 구현입니다

저장소 전체에 **대운 계산은 존재하지 않습니다.** 문서·폴리시·관문에만 이름이 나옵니다.

```
saju.js      pillars({ y, m, d, hour, city })     → 년·월·일·시 4주만.  gender 인자 없음
fortune.js   of(mine, today)                       → 6항목 점수 + 십신. gender 인자 없음
server/lib/fortune.mjs:101-104                     → 위 둘을 그대로 호출
```

`grep -rn "大運\|대운"` 의 결과는 `docs/` · `privacy.html` · `verify-onboarding.mjs` 뿐입니다.
**엔진 안에는 한 줄도 없습니다.**

그래서 「반영(①)」을 고르시면 실제로 만들어야 하는 것은 세 덩어리입니다.

| # | 만들 것 | 왜 만만치 않은가 |
|---|---|---|
| 1 | **대운 방향** — 순행/역행 (년간의 음양 × 성별) | 규칙 자체는 단순. 이건 쉬운 쪽 |
| 2 | **대운수** — 출생일에서 앞/뒤 절기까지의 일수 ÷ 3 | 절기표(`solar-terms.json`)는 이미 있으나, **경계 처리(3으로 나눈 나머지·절입 시각)에 유파차**가 있어 「무엇이 정답인가」를 먼저 정해야 함 |
| 3 | **점수에 반영** — `Fortune.of()` 에 대운 간지를 입력으로 추가 | 6항목 점수 전체가 바뀝니다. **지금 이용자에게 매일 가고 있는 숫자가 달라집니다** |

3번 때문에, 이건 「기능 추가」가 아니라 **상품의 내용을 바꾸는 일**입니다.

## 6-3 ★ 그리고 갈라짐 — 웹은 성별을 묻지 않습니다

저장소가 가장 조심하는 것이 **「웹과 LINE 의 운세가 갈라지는 것」**입니다
(STATUS §8-3 / CLAUDE.md — 양쪽 다 그럴듯한 숫자라 대조 전엔 아무도 모릅니다).

그런데 지금:

- 사이트 무료 진단은 성별을 **묻지 않습니다.** `index.html:3297` 이 `gender:'U'` 를 고정으로 보냅니다
- 그것을 관문이 **강제**합니다 — `verify-onboarding` 「この画面は性別を訊いていません」(650행 부근)
- 「사이트 폼 불변」은 §0 의 지시사항입니다

**성별을 반영하면, 같은 사람이 웹에서 보는 운세와 LINE 에서 받는 운세가 달라집니다.**
엔진을 공유(`node:vm`)해도 **입력이 다르면 갈라집니다.** 이것이 이 결정의 진짜 무게입니다.

## 6-4 답하실 수 있는 세 갈래

| 안 | 내용 | 대가 | 이용자에게 |
|---|---|---|---|
| **(다) 현행 유지 — 저장만** | 아무것도 안 함 | 없음. 폴리시·관문·문서 전부 지금 그대로 맞음 | 변화 없음 |
| **(나) LINE 만 반영** | 대운을 만들고, 성별을 가진 LINE 이용자에게만 반영 | **웹과 LINE 이 갈라짐**(§6-3). 갈라짐을 아는 채로 받아들이는 결정이 필요. 폴리시 2곳 + 관문 1곳 개정 | 답한 사람과 안 한 사람의 운세가 달라짐 |
| **(가) 전면 반영** | (나) + 사이트 폼에도 성별 추가 | 「사이트 폼 불변」 지시의 해제가 필요. 페이지 수정 4곳 함정(STATUS §8-8)·관문 개정 | 웹 진단 단계가 1개 늘어남(이탈 요인) |

**셋 다 정답일 수 있습니다.** 다만 (나)·(가)를 고르시면 **별도 계획서 1개**(대운 계산의 유파 결정 포함)가 먼저 필요하고, 그 전에 지금 배신 중인 운세 점수가 바뀐다는 것을 받아들이셔야 합니다.

## 6-5 B1(프로필 편집)은 이 결정을 기다릴 필요가 없습니다

`/profile` 이 하는 일은 **이미 수집 중인 값을 고치게 해주는 것**입니다.
성별을 대운에 쓰는지 여부와 무관하게, 지금도 값은 저장되고 있고 정정 수단만 없습니다
(온보딩 중에는 `action=fix&s=bgender` 로 고칠 수 있으나, 온보딩이 끝나면 길이 없습니다 —
`onboarding.mjs` 618행).

따라서 **(다)를 고르셔도 B1 은 착수 가능합니다.** STATUS 의 「A4 승인 후 B1」은
②문안이 미게시였던 시점의 기재이며, 그 전제는 §6-1 대로 해소되었습니다.
